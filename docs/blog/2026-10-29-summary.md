# proj-janitor 项目进展（2026-10-29）

## Rust 清理确认安全回归

Rust CLI 集成测试现覆盖两种 JSON 清理行为：

- `clean --json --apply` 未提供 `--yes` 时返回失败，JSON 计划仍可解析，目标制品保留。
- `clean --json --apply --yes` 成功并删除计划中的制品。

测试并入现有 `TC-79` fixture，不增加测试方法或依赖；测试报告的 P2 建议已标记完成。

## 多项目恢复完整性预检

Python 与 Rust 的多项目归档恢复回归现验证两种失败状态：若后续归档的 SHA-256 不匹配，恢复会在写入前失败；若摘要有效但后续归档无法解压，之前已恢复的项目保留、错误中列出其路径，失败目标不会留下。批量恢复不自动回滚。

## CLI 入口与清理规则

Python 与 Rust 的 CLI 测试现验证 `--help` 和 `--version` 无需子命令即可成功退出；两种实现的 `clean --list-rules` 也可在无 ROOT 时列出规则。Python/Rust 的 `--rules node,build` 只列出选中规则，未知规则报错且不删除制品；`--apply --yes --rules node` 仅删除 `node_modules`，保留 `target`。

## Git 子模块轻量备份与恢复

Python 和 Rust 两种实现现允许干净、远端可恢复且带未初始化 `evals/cline-bench` 子模块的仓库走 Git 轻量策略。备份仅保存主仓库提交和 gitlink，不生成压缩包；恢复时逐层初始化并检出子模块固定提交，全部成功后才发布目标目录。被修改、提交位置不匹配、URL 不受支持或恢复时远端提交不可用的情况会失败或回退归档，避免把不完整内容当作成功恢复。

本地 parent/child Git fixtures 验证了两种实现的备份策略、恢复内容、gitlink SHA、已初始化与未初始化子模块识别，以及取回失败时不生成目标目录。递归深度限制为 32 层。Git 轻量备份不镜像子模块对象，未来恢复仍依赖子模块远端可用。Cline 的 dry-run 在启用子模块支持后仍因 `.gitattributes` 中的 Git LFS 属性选择 archive；本机没有 `git-lfs`，其 `assets/docs/demo.gif` 当前是 133 字节 LFS 指针，指向 19 MB 的远端对象。因此这次子模块改动本身不会让 Cline 改用 Git 策略。

## 扫描输出与备份策略说明

Python/Rust 扫描用例现检查 JSON 字段和文本表头/项目名。子模块轻量支持后，配置了受支持 GitHub 子模块的干净仓库可使用 Git 策略；Cline 当前仍因 Git LFS 属性回退 archive。Rust 的实际备份和 dry-run 输出现在也会显示 archive fallback reason，避免只看到 `[archive]` 而不清楚原因。

## 较大归档恢复演练

对用户指定的 schema v2 归档 manifest 执行 `verify --json` 和临时 `restore --dest --json`；恢复后的扫描大小为 3,478,246,657 字节，与 `source_bytes` 一致。恢复项目可被 scanner 发现，临时副本已清理，源归档及 manifest 未修改。此演练覆盖 archive 到新目标目录的恢复，不代表原位恢复、权限/ACL 或业务启动已验证。
