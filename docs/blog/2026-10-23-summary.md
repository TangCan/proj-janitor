## 6. 结项复核确认的 4 项缺陷

以下缺陷均在 `v0.1.0` 中确认存在，当前**全部未修复**：

| 编号 | 等级 | 问题 | 影响 |
| --- | --- | --- | --- |
| DEF-001 | 中 | `clean --json` 在 JSON 后追加人类可读提示 | 严格 JSON 解析器报 `Extra data`，脚本消费失败 |
| DEF-002 | 中 | `coverage` 规则匹配任意同名目录 | 可能把源码目录当作覆盖率产物删除 |
| DEF-003 | 中 | 单项目归档异常中断整批备份，且不生成 manifest | 批量备份不可靠，可能留下无清单的部分归档 |
| DEF-004 | 低 | `clean --list-rules` 仍要求 `ROOT` 参数 | 无法直接查看规则，必须写成 `clean . --list-rules` |

### 6.1 本日复核证据

- **DEF-001**：在一个含 `node_modules` 的临时项目中执行 `clean --json`，stdout 先输出合法 JSON，末尾追加 `Dry run. Re-run with --apply to delete these items.`；`json.load()` 抛出 `JSONDecodeError: Extra data`。
- **DEF-002**：创建 `app/coverage/keep.py` 后执行 `clean`，`coverage` 目录被 `node` 规则列入清理计划，确认存在误匹配。
- **DEF-003**：构造两个项目，第二个项目含权限为 `000` 的文件；执行 `backup` 后退出码为 1，stderr 出现 `PermissionError` traceback，两个归档均已生成，但没有运行清单。
- **DEF-004**：执行 `projjan clean --list-rules`，argparse 报 `the following arguments are required: roots`，退出码为 2。

上述复核均在 `/tmp/opencode` 下的临时目录完成，没有修改或删除真实项目。

## 8. 关键设计与安全约束

- 仅使用 Python 标准库，运行时无第三方 Python 依赖；要求 Python `>=3.10`，当前验证环境为 3.12.3，Git 实测 2.43.0。
- `clean` 默认 dry-run，只有显式 `--apply` 才执行删除；非交互环境还必须提供 `--yes`，否则退出码为 2。
- 永不删除项目根目录和 `.git`；只删除白名单构建产物，路径必须位于项目根目录内。
- 不跟随符号链接，也不进入已匹配目录继续扫描。
- `backup` 默认排除构建产物；`--include-artifacts` 和 `--always-archive` 可强制归档。
- URL-only 仅适用于受支持的 GitHub 远程，且工作区干净、无 stash/submodule/LFS、所有本地分支已推送、所有本地 tag 均已推送到远程、ignored 文件均为可重建产物。HTTPS 远程允许内嵌 PAT，但记录和输出必须脱敏（见第 14、15 节）。
- 任一 Git 检查失败或信息不确定时，保守回退为 `tar.gz`，并在 manifest 中记录 `fallback_reason`。
- manifest 使用 `schema_version: 2`，区分 `git` 与 `archive` 记录，归档记录包含 SHA-256。
- 退出码约定：成功 0；根目录或部分处理失败 1；拒绝删除、缺少确认参数或用户取消 2。
- 单层项目发现：默认只检查根目录本身和直接子目录，不递归遍历整个文件树。

- `clean --list-rules` 当前需要占位根目录，推荐写 `projjan clean . --list-rules`。
- `clean --json` 当前不是严格纯 JSON，脚本消费前需评估 DEF-001。
- 对含 `coverage` 源码目录的项目，先不要执行 `clean --apply`，等待 DEF-002 修复或显式调整规则。
- 批量备份前先修复 DEF-003，或改为分批执行并人工检查归档与 manifest。

## 13. 结论

本日完成了 `proj_janitor` 的结项文档体系和版本基线收尾：10 份结项文档、1 份编制清单、本地 `v0.1.0` 标签和文档提交均已就位，结项复核时 38 项自动化测试全部通过，当时工作区干净。项目已经具备内部交付和日常使用的基础条件。

结项复核阶段没有新增功能或修复缺陷，反而确认了 4 项未修复问题；同日后续完成了 PAT URL、远程 tag 校验和备份目录布局三项调整，见第 14～16 节。当前仍不应把项目描述为“可以无人值守批量备份”或“可以安全消费 `clean --json`”；对真实目录执行清理前，也必须人工审查计划。下一阶段的重点应放在 DEF-001～DEF-003 的修复、文档一致性修订、远程仓库推送和内部验收上，而不是扩大删除范围。

## 14. 同日后续变更：允许内嵌 PAT 的 GitHub URL

结项复核后调整了 URL-only 的远程 URL 规则：

- HTTPS GitHub URL 现在允许内嵌凭据，例如 `https://token@github.com/owner/repo.git` 和 `https://user:token@github.com/owner/repo.git`。
- URL-only 记录、dry-run 输出和 manifest 只保存脱敏后的 `https://github.com/owner/repo.git`，不会写入用户名或令牌。
- 非 GitHub 远程的回退原因改为 `remote is not a supported GitHub URL`。
- 自动化测试从 38 项增加到 42 项，新增凭据 URL 接受、URL 脱敏、可恢复性判定、manifest 脱敏和 CLI 输出脱敏用例。
- `xtask_todo` 实测已不再因 PAT 回退；当时仍因 27 个本地 tag 回退为归档，tag 策略随后在第 15 节调整。
- 归档仍会包含 `.git/config`；如果远程 URL 内嵌 PAT，归档也会包含该凭据。执行归档前应先清理远程 URL 或限制归档访问权限。

## 15. 同日后续变更：允许已推送的本地 tag

在第 14 节之后，tag 规则由“存在任何本地 tag 就回退归档”改为“只阻止未推送或与远程不一致的本地 tag”：

- 没有本地 tag 时，不发起额外网络查询，行为与之前一致。
- 存在本地 tag 时，执行 `git ls-remote --tags --refs <remote>`，读取远程 tag 的原始对象 ID。
- 本地 tag 的 `%(objectname)` 与远程同名 tag 的对象 ID 逐项比较；轻量 tag 比较 commit ID，附注 tag 比较 tag 对象 ID。
- 远程缺少同名 tag：回退原因 `local tag is not pushed: <name>`。
- 同名 tag 指向不同对象：回退原因 `local tag differs from remote: <name>`。
- 远程不可达或查询失败：回退原因 `cannot verify local tags on remote`，保守生成归档。
- 自动化测试从 42 项增加到 47 项，新增远程 tag 读取、已推送 tag、仅本地 tag、tag 指向不一致和远程查询失败用例。
- `xtask_todo` 实测已变为 URL-only：

  ```text
  [git] xtask_todo: https://github.com/TangCan/xtask_todo.git @ 2d096721598b
  ```

  其 27 个本地 tag 与远程 27 个 tag 的名称和对象 ID 全部一致。
- `verified` 字段仍保持 `local-ref` 兼容值；本次新增的是 tag 准入校验，并未联网验证 HEAD 提交仍存在于远程。
- 该规则要求远程查询可用；使用带 PAT 的 HTTPS URL、`gh` credential helper 或 SSH 均可，但归档仍然包含 `.git/config`，因此带凭据的远程 URL 在归档前仍应先清理。

## 16. 同日后续变更：备份目录按项目归档

此前每次实际备份都会创建 `backup-YYYYmmdd-HHMMSS/` 运行目录；纯 `git` 备份即使只有一份 700 字节的清单，也会留下一个目录。第一次调整把清单放到 `--dest` 顶层，但连续两次轻量备份仍会在顶层生成两个 `manifest-*.json`，没有按项目归集。最终布局调整为：

- `--dest` 下每个项目使用一个稳定的项目目录，不再创建 `backup-.../` 运行目录。
- 纯 `git` 备份只在项目目录下写清单，不创建按运行时间命名的目录：

  ```text
  backups/
  └── xtask_todo/
      ├── manifest-20261023-122828.json
      └── manifest-20261023-122832.json
  ```

- 需要归档的项目把清单和归档放在同一个项目目录；同一项目不同时间的文件共用该目录，文件名带运行时间戳：

  ```text
  backups/
  ├── xtask_todo/
  │   ├── manifest-20261023-103117.json
  │   └── xtask_todo-20261023-103117.tar.gz
  └── another_project/
      ├── manifest-20261023-103117.json
      └── another_project-20261023-103117.tar.gz
  ```

- 一次运行包含多个项目时，每个项目目录各写一份只包含该项目记录的清单；不再产生根级运行清单。
- 不同根目录下存在同名项目时，项目目录追加 8 位路径哈希，例如 `app-1a2b3c4d/`。
- 同一秒内重复备份同一项目时，清单和归档文件名追加 `-2`、`-3`，不会覆盖已有文件。
- `manifest` 的 schema 仍为 v2，单份清单的 `records` 只包含当前项目；`archive` 记录仍保存归档的绝对路径。旧版本生成的 `backup-*` 目录不会自动迁移或删除。
- 新增 `test_repeated_archives_share_project_directory` 和 `test_batch_run_writes_manifest_per_project`，验证同一项目连续两次归档进入同一个项目目录，以及批量运行按项目分别写清单；测试总数从 47 项增加到 49 项。
- 实测 `xtask_todo` 连续两次纯 `git` 备份均写入 `xtask_todo/`，生成两个 700 字节的 `manifest-*.json`。
- 旧版本生成的 `backup-*` 目录不会自动迁移或删除；如果其中仍保留旧规则生成的归档，尤其包含 `.git/config` 和历史凭据的归档，应单独确认并清理或加密隔离。
