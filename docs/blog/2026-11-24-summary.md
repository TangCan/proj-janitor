## 修复前的复核结论

- 最后一次 CI 全绿为 `v0.7.57`（[run 44031100331](https://github.com/TangCan/proj-janitor/actions/runs/44031100331)）；`v0.7.58`～`v0.7.88` 共 31 个 Rust tag 的 CI 连续失败（首次：[run 44081988313](https://github.com/TangCan/proj-janitor/actions/runs/44081988313)）。
- 失败并非归档安全逻辑回归：跨实现兼容与 coverage 作业通过，CodeQL 另行运行且通过；问题集中在提示文案断言、`clean` 双端差异与格式漂移。

| 检查 | 修复前结果 | 根因 |
| --- | --- | --- |

| `cargo fmt --check` | 失败 12 处 | `archive.rs` 1、`init.rs` 3、`rust_cli.rs` 8；CR-189 后未格式化 |
| Rust 依赖审计 | 失败 | 新披露 RUSTSEC-2026-0592（`url` 2.5.8） |

## 本次修复要点

1. **`clean` 双端对齐**：`_collect_projects` 增加 `warn_unmarked` 开关，`clean` 传 `False`；Python 与 Rust 一致，且不再建议一个 `clean` 不支持的选项。
2. **断言与提示意图对齐**：`--always-archive` 断言收窄为默认提示 `will use git-only metadata`；Rust 重叠根去重用例改为断言 CR-161 的 `clean --apply` 提示。
3. **格式与依赖**：`cargo fmt` 清零；`url` 升级到 2.5.9（项目只用 `Url::parse`，未调用 `origin()`，实际暴露面低，但审计门禁按 lockfile 判定）。
4. **文档纠偏**：README 的 Python 安装版本从 `0.1.52` 修正为 `0.1.88`，发布时同步为 `0.1.89`；06 / 09 记录修复与发布。

## 使用侧提示

- 推荐升级到 `0.1.92` / `0.7.92`：包含 `url` 2.5.9、`clean` 提示对齐、V-03 数字/同形字规则与 LFS batch 双端对齐。全角/数学/带圈 `CON` 或全角 `ＣＯＭ１` 会被拒绝；`COM0`、`COM10`、西里尔 `СОН` 等仍可使用。
- Python `clean` 不再输出无标记 ROOT 提示；`backup` / `scan` 的提示保持不变。
- 重要项目用 `--always-archive`；加密与解密使用同一 passphrase；不要对不可信归档使用 `--no-verify`。
