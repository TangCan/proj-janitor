- **本轮（CR-088）`verify --check-remote` 远端可达性预检已完成实现、测试与全套文档记录**，并于 2026-11-05 提交到 main（`91aa4cb`，已推送）。该变更自 2026-11-04 起存在于仓库源码：Python 与 Rust 的 `verify` 新增可选 `--check-remote`，对 Git-only 记录执行一次 `git ls-remote`（单条最长等待 30 秒，`GIT_TERMINAL_PROMPT=0`，参数列表调用不经 shell），只读取引用列表、不下载对象，给出四种状态：
  - `remote-verified`：远端至少一个引用指向记录的提交，`--json` 的 `remote.refs` 为去重后按字典序排序的引用列表（注解 tag 已去掉 `^{}` 后缀）。
  - `remote-moved`：远端可达但无引用指向该提交；恢复按提交 SHA 抓取，提交仍可能从其它引用可达。
  - `remote-unreachable`：`git ls-remote` 失败或超时，无法确认远端；命令仍先输出完整报告，再以退出码 `1` 结束（stderr 输出 `error: one or more remotes could not be reached`）。
  - `remote-skipped`：manifest 的 URL 含用户名、口令、query 或 fragment；此时不会把该 URL 传给 Git，也不联网。
- 安全与兼容边界：默认行为保持离线，不带该选项时不产生任何 Git 子进程，文本与 JSON 输出结构与之前完全一致；`remote.url` 在输出中脱敏；`restore` 流程与 manifest schema v2 不变；archive/`git_bundle` 记录不受影响。本轮还修正了 Python 在 stdout/stderr 合并采集时“报告尚未 flush 就先写错误行”的缓冲顺序问题（stderr 消息前先 `sys.stdout.flush()`），并在跨实现兼容脚本中固化为逐字节比对。

- **本轮新增（CR-089）`restore --check-remote` 恢复前远端预检**：把 CR-088 的同一 `probe_remote`/`_probe_remote` 集成进 Python 与 Rust 的 `restore` 流程。`restore` 新增可选 `--check-remote`，在 SHA-256 校验与交互确认之后、创建任何目标目录之前，对每个 Git-only 计划执行一次 `git ls-remote`（单条最长 30 秒，`GIT_TERMINAL_PROMPT=0`，参数列表调用不经 shell，只读引用列表、不下载对象）；任一记录 `remote-unreachable` 时整批不开始，报 `cannot restore <项目>: remote <脱敏URL> is unreachable (<原因>)` 并返回退出码 `1`。复用既有预检实现意味着无需 manifest schema 变更、不下载对象；含凭据或 query/fragment 的 URL 不联网、不传给 Git；`archive`/`git_bundle` 记录忽略该选项；默认仍保持离线；缺失 `remote_url`/`commit` 报 `incomplete git restore plan`。这直接缓解 R-02 的恢复阶段风险，把“恢复前先验证远端可用”从两条显式命令简化为恢复流程内的一步。
