## 3. 总体描述

### 3.1 产品定位

`proj_janitor` 是一个仅依赖 Python 标准库的本地命令行工具，面向开发机或工作站上的项目目录，提供四项能力：

1. `scan`：发现项目并展示体积、修改时间与 Git 状态；
2. `backup`：对可恢复的 GitHub 项目仅记录 URL 与提交，对其他项目生成 `tar.gz` 归档；
3. `restore`：按 manifest 恢复 Git 项目或归档项目，归档默认校验 SHA-256；
4. `verify`：只读校验 archive SHA-256；Git 记录只检查 manifest 元数据。
5. `clean`：按规则生成制品清理计划，并在显式确认后删除。

工具不启动网络服务；除 `backup` 校验远程 tag 和 `restore` 克隆 Git 远程外，不主动访问网络。它不替代版本控制或专业备份系统。

### 3.2 设计目标

| 目标 | 说明 |
| --- | --- |
| 本地优先 | 所有操作在本机文件系统完成，不依赖远程服务 |
| 安全保守 | 清理默认仅预览；删除前校验根目录、符号链接和 `.git` |
| 可审计 | 备份生成 manifest，归档记录 SHA-256 |
| 低依赖 | 运行时不引入第三方 Python 包 |
| 可回退 | 无法确认 GitHub 可恢复时回退为归档备份 |
| 可恢复 | manifest 可驱动 Git/归档恢复；归档校验 SHA-256，安全解压且不覆盖 |
| 可测试 | 扫描、备份、恢复、清理和 CLI 均有自动化测试 |

### 3.3 用户与使用场景

| 用户类型 | 典型场景 |
| --- | --- |
| 个人开发者 | 盘点旧项目体积，删除缓存和依赖目录 |
| 维护人员 | 在迁移或归档前生成项目备份清单 |
| 评审人员 | 核对工具能力、限制和交付证据 |

典型流程为：先执行 `scan` 了解项目；再执行 `backup --dry-run` 检查策略；确认目标目录后执行备份；最后执行 `clean` 预览，必要时加 `--apply --yes` 删除。

### 3.4 运行环境

| 项目 | 要求 |
| --- | --- |
| 操作系统 | Python 3.12 在 Linux/macOS/Windows CI 验证；Rust stable 在 Linux/macOS/Windows CI 验证；更广的系统版本和文件系统未验证 |
| Python | 3.10 及以上 |
| Rust | 1.88 及以上（MSRV） |
| 运行时依赖 | Python 无第三方运行时依赖；Rust 使用 Cargo.lock 固定的 crate 依赖 |
| 外部程序 | Git 为 Git 状态、URL-only 和 Git 恢复所需；含 Git LFS 属性的项目还要求安装 Git LFS |
| 安装方式 | Python 源码安装；Rust `cargo install --locked` |
| 入口 | Python `projjan` / `python3 -m proj_janitor`；Rust `projjan` |

### 3.5 约束与假设

- 项目发现仅覆盖扫描根本身及其直接子目录，不递归搜索。
- 备份和清理均以“项目根”为单位，不处理项目内部任意路径。
- Git 可恢复性判定基于本地引用和本地 Git 命令结果；只有存在本地 tag 时才通过 `git ls-remote --tags --refs` 查询远程 tag。
- `restore` 的 Git 策略会联网克隆 manifest 中的远程；不预检远程提交是否仍存在。
- 工具不负责备份目标目录的容量、权限、加密、保留期和异地容灾。
- 工具不解析项目内容，不保证归档中不含敏感信息。
- 当前配置 GitHub `origin`；Rust `v0.2.5` 已发布。

### 4.3 FR-001 项目发现

**需求描述**：工具应从一个或多个扫描根发现项目，支持扫描根本身是项目、扫描根的直接子目录是项目两种布局，并对重复项目去重。

**输入**：一个或多个 `ROOT` 路径；`scan` 可附加 `--all`。

**规则**：

1. 每个扫描根必须存在且为目录；不存在或不是目录时，向标准错误输出错误并继续处理其他根。
2. 若扫描根自身包含项目标记，则只将扫描根作为项目，不再扫描其子目录。
3. 若扫描根自身不是项目，则仅检查其直接子目录，不递归进入更深层。
4. 默认跳过名称以 `.` 开头的子目录、符号链接子目录和没有项目标记的子目录。
5. 指定 `--all` 时，没有标记的直接子目录也作为项目；以 `.` 开头的目录和符号链接目录仍跳过。
6. 多个扫描根产生同一路径的项目时，只保留首次出现的项目。
7. `backup` 和 `clean` 不使用 `--all`，只处理有标记的项目。

**输出**：项目列表；根路径错误信息。

**验收判据**：

- 含 `pyproject.toml` 的目录被发现，未标记的普通目录默认不被发现。
- 加 `--all` 后未标记目录被发现。
- 扫描根本身是项目时，只返回该根项目。
- 不存在的根返回非零退出码，并输出 `root does not exist: ...` 或对应错误。
- 重叠根产生的重复路径只出现一次。

**追踪**：`scanner.discover_projects`、`scanner.is_project`、`cli._collect_projects`；`test_discovers_marked_projects_only`、`test_include_unmarked`、`test_missing_root_raises`。

### 4.4 FR-002 扫描根即项目

**需求描述**：当用户直接对一个项目目录执行扫描或备份时，工具应将该目录识别为项目，而不是错误地只检查其子目录。

**规则**：

- 扫描根含任一项目标记时，项目名称为该根目录名，路径为该根路径。
- 该行为优先于“只扫描直接子目录”的默认规则。

**验收判据**：对含标记的项目根执行 `scan`，输出该项目本身；不会因其子目录无标记而返回空结果。

**追踪**：`scanner.discover_projects` 第 25–29 行；`test_root_can_be_a_project`。

### 4.5 FR-003 项目标记识别

**需求描述**：工具应使用固定标记集合判断目录是否为项目。

**标记集合（16 项）**：

| 类别 | 标记 |
| --- | --- |
| 版本控制 | `.git`、`.hg`、`.svn` |
| Python | `pyproject.toml`、`setup.py`、`setup.cfg`、`requirements.txt` |
| JavaScript/Node | `package.json` |
| Rust | `Cargo.toml` |
| Go | `go.mod` |
| C/C++ | `CMakeLists.txt`、`Makefile`、`meson.build` |
| JVM | `build.gradle`、`build.gradle.kts`、`pom.xml` |

**规则**：

- 标记既可以是文件也可以是目录；只检查名称，不读取内容。
- 返回的标记顺序与 `PROJECT_MARKERS` 定义顺序一致，仅包含实际存在的标记。
- 标记集合外的新技术栈不会被自动识别，需修改代码或显式使用 `--all`。

**验收判据**：含任一标记的目录被发现；标记列表与实际存在的标记一致；不含任何标记的目录默认不被发现。

**追踪**：`config.PROJECT_MARKERS`、`scanner.is_project`；扫描测试夹具。

### 4.6 FR-004 体积与修改时间统计

**需求描述**：工具应统计项目的常规文件总字节数，并报告最近修改时间。

**规则**：

1. 使用不跟随符号链接的目录遍历；符号链接目录不进入。
2. 仅累计常规文件的 `st_size`；目录本身不计入。
3. 文件符号链接按链接自身统计，不读取目标文件。
4. 最近修改时间取所有被统计常规文件 `st_mtime` 的最大值。
5. 输出使用本机本地时间的带时区偏移 `datetime`（由 UTC 时间转换得到）；JSON 使用 `isoformat()`，包含偏移量。
6. 空项目或没有可统计文件时，最近修改时间为 `null`。

**验收判据**：项目体积等于夹具文件字节数之和；最近修改时间非空；无文件项目返回 `0` 字节且时间为 `null`。

**追踪**：`scanner.measure_tree`、`scanner.scan_project`、`models.Project`；`test_scan_project_without_git`。

### 4.7 FR-005 Git 状态读取

**需求描述**：项目根存在 `.git` 时，工具应读取当前分支和工作区状态。

**规则**：

1. 分支名通过 `git rev-parse --abbrev-ref HEAD` 获取；分离头指针时可能得到 `HEAD`。
2. 工作区状态通过 `git status --porcelain` 获取；有输出为 `dirty`，无输出为 `clean`。
3. 任一 Git 命令失败或超时（10 秒）时，对应字段为未知；分支未知显示 `-`，状态未知显示 `unknown`。
4. 不存在 `.git` 时，Git 状态为 `null`，文本显示 `-`。
5. Git 状态读取不修改仓库，不执行 fetch、pull、push 或 checkout。

**验收判据**：干净仓库显示 `clean`；修改文件后显示 `dirty`；非 Git 项目显示 `-`；Git 命令失败不导致扫描崩溃。

**追踪**：`scanner.read_git_state`、`scanner._git_run`、`models.GitState`；`test_scan_project_reports_clean_and_dirty_git_states`。

### 4.8 FR-006 扫描文本/JSON 输出

**需求描述**：`scan` 应以人类可读表格或 JSON 输出项目清单。

**文本输出**：

- 表头为 `PROJECT`、`SIZE`、`BRANCH`、`STATE`、`MARKERS`、`MODIFIED`。
- 体积使用 `B`、`KiB`、`MiB`、`GiB`、`TiB`，非字节单位保留一位小数。
- 无项目时向标准错误输出 `No projects found.`。
- 有项目时表格输出到标准输出。

**JSON 输出**：

- 顶层为数组；每个元素包含 `name`、`path`、`size_bytes`、`last_modified`、`markers`、`git`。
- `git` 为 `null` 或 `{ "branch": string|null, "dirty": bool|null }`。
- 使用 UTF-8、`ensure_ascii=False`、两空格缩进。

**退出码**：所有根处理成功返回 `0`；任一扫描根失败返回 `1`，即使其他根成功。

**验收判据**：JSON 可解析且字段齐全；无项目时标准错误包含固定提示；根错误时退出码为 `1`。

**追踪**：`cli._cmd_scan`、`cli._project_json`、`scanner.format_projects`；`test_scan_json`、`test_missing_root_reports_error`。

### 4.9 FR-007 GitHub URL 校验

**需求描述**：仅当项目的远程 URL 是受支持的 GitHub URL 时，才允许进入 URL-only 判定；HTTPS 形式允许内嵌 PAT，但持久化和输出必须脱敏。

**接受形式**：

- `https://github.com/<owner>/<repo>` 或 `https://github.com/<owner>/<repo>.git`
- `https://<user>[:<token>]@github.com/<owner>/<repo>[.git]`（内嵌凭据仅用于访问私有仓库）
- `ssh://git@github.com[:22]/<owner>/<repo>` 或对应 `.git` 形式
- `git@github.com:<owner>/<repo>` 或对应 `.git` 形式

**拒绝情形**：

- HTTP、非 HTTPS 且非 SSH 的协议；
- 非 GitHub 主机；
- 本地路径、`file://`、其他协议；
- 多余路径层级、查询字符串、片段；
- 空 owner 或空 repo；
- 端口不是 443（HTTPS）或 22（SSH）。

**脱敏规则**：HTTPS GitHub URL 在写入 `GitRecovery`、manifest 或 CLI 输出前，去除用户名、密码/token、查询字符串和片段，只保留 `https://github.com/<owner>/<repo>[.git]`。

**验收判据**：支持形式全部接受；带凭据的 HTTPS URL 可判定为可恢复，但输出和 manifest 不含凭据；非 GitHub、歧义路径和非法端口全部拒绝。

**追踪**：`scanner.is_github_remote_url`、`scanner._valid_github_path`、`scanner.sanitize_remote_url`；URL 校验、凭据接受和脱敏测试。

### 4.10 FR-008 URL-only 可恢复性判定

**需求描述**：工具应保守判断项目能否仅凭 GitHub 远程 URL 和提交号恢复；只有全部条件满足时才选择 URL-only 备份，否则回退归档。

**全部满足条件**：

1. 项目存在 `.git` 且不是分离头指针。
2. `git status` 成功且工作区干净。
3. 可检查 stash，且不存在 stash 条目。
4. 当前分支配置了远程，且存在上游分支。
5. 远程 URL 通过 FR-007 校验。
6. HEAD 可用，且 HEAD 已包含于上游。
7. 本地分支均完全推送，且不存在未推送提交。
8. 所有本地 tag 均已推送，且与远程同名 tag 指向同一对象；没有本地 tag 时不查询远程。
9. `.gitmodules` 配置有效，所有子模块 URL 为无凭据的 GitHub URL 或相对 GitHub 主仓库的 `./` / `../` URL；未初始化子模块目录必须不存在或为空，已初始化子模块必须位于记录的 gitlink 提交且工作区干净，嵌套子模块也满足相同条件。
10. 若存在 Git LFS 属性，必须能执行 `git lfs version`；不允许 `.lfsconfig` 或自定义 LFS URL，LFS 对象由默认 GitHub endpoint 提供。
11. 被忽略的文件仅限已知制品模式和固定的可重建生成路径。

**输出**：`GitRecovery`，包含是否可恢复、失败原因、远程名、远程 URL、分支、提交、上游与验证标记。

**规则**：

- 验证标记固定为 `local-ref`，表示本地分支和提交依据本地引用判断；存在本地 tag 时会额外查询远程 tag 引用。
- tag 校验失败时给出 `local tag is not pushed: <name>`、`local tag differs from remote: <name>` 或 `cannot verify local tags on remote`。
- 任一条件无法检查时按不可恢复处理，并给出原因。
- 判定失败不阻止备份，而是回退为归档。

**验收判据**：已完整推送且干净的仓库（含受支持子模块或 Git LFS）为可恢复；脏工作区、未推送提交、stash、非受支持远程、Git LFS 缺失或使用自定义 endpoint、未推送或对象不一致的本地 tag、被忽略的非制品/非生成文件、含凭据的子模块 URL、提交位置不匹配或不受支持 URL 的子模块均不可恢复；失败原因可读。

**追踪**：`scanner.inspect_git_recoverability`、`scanner._verify_local_tags`、`models.GitRecovery`、Rust `project::inspect_submodules`；Git 可恢复性测试、tag 校验测试、凭据 URL 测试和 TC-93～TC-95。

### 4.11 FR-009 备份策略选择

**需求描述**：`backup` 应为每个项目选择 `git` 或 `archive` 策略，并给出可审计的原因。

**决策顺序**：

1. 指定 `--include-artifacts`：强制归档，原因 `include_artifacts`。
2. 否则指定 `--always-archive`：强制归档，原因 `always_archive`。
3. 否则若 FR-008 判定可恢复：选择 `git`，不生成归档。
4. 若可恢复性失败原因为 `submodule URL contains credentials`，默认备份报错且不写归档或 manifest；显式 `--always-archive` / `--include-artifacts` 才允许用户强制归档。
5. 其他情况归档，原因取可恢复性失败原因；没有原因时使用 `not recoverable from GitHub`。

**验收判据**：默认对干净且已推送的 GitHub 项目生成 `git` 记录；一般不可恢复项目生成归档并记录失败原因；含凭据的子模块 URL 默认拒绝写盘；`--always-archive` 覆盖 `git` 策略；`--include-artifacts` 覆盖前两者。

**追踪**：`backup.prepare_backup`；`test_pushed_repo_is_recorded_without_archive`、`test_dirty_repo_falls_back_to_archive`、`test_always_archive_overrides_git_strategy`、`test_include_artifacts_forces_archive`。

### 4.12 FR-010 归档备份与 SHA-256

**需求描述**：归档策略应生成 `tar.gz` 文件，计算并记录 SHA-256。

**规则**：

1. 每个项目使用 `DEST/<项目名>/` 项目目录；同一项目的不同时间备份共用该目录。
2. 归档名默认为 `<项目名>-YYYYMMDD-HHMMSS.tar.gz`；同一秒或同名冲突时追加 `-2`、`-3` 等后缀。
3. 归档与 `manifest-YYYYMMDD-HHMMSS.json` 位于同一项目目录。
4. 归档内容以项目名称为顶层目录。
5. 默认排除 `python-cache`、`python-env`、`node`、`build`、`editor` 规则匹配的制品；`--include-artifacts` 时全部包含。
6. 归档包含 `.git` 目录；该行为保证仓库元数据不丢失，但会增大归档体积，也可能保留 `.git/config` 中的凭据。
7. SHA-256 以 1 MiB 分块读取归档文件计算，使用小写十六进制。
8. 归档记录 `archive`、`archive_bytes`、`source_bytes`、`sha256`。

**验收判据**：归档可被 `tarfile` 打开；源码文件存在；默认不含 `node_modules`；加 `--include-artifacts` 后包含；记录 SHA-256 与文件实际哈希一致；同名项目生成不同归档名。

**追踪**：`backup.run_backup`、`backup.backup_project`、`backup.sha256_file`、`backup._unique_archive_name`；`test_backup_writes_archive_and_manifest`、`test_backup_can_include_artifacts`、`test_duplicate_names_are_disambiguated`。

### 4.13 FR-011 manifest v2

**需求描述**：每次实际备份运行应为每个项目生成 `DEST/<项目名>/manifest-YYYYMMDD-HHMMSS.json`，记录运行参数和该项目备份结果；批量运行按项目分别写清单，不再生成根级运行清单。

**顶层字段**：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `schema_version` | 整数 | 固定为 `2` |
| `created_at` | 字符串 | UTC ISO 8601 时间 |
| `tool` | 字符串 | 固定为 `proj-janitor` |
| `version` | 字符串 | 生成清单的实现版本；Python 为 `0.1.0`，Rust main 候选 Cargo 版本为 `0.2.6`（尚未发布） |
| `include_artifacts` | 布尔 | 是否包含制品 |
| `always_archive` | 布尔 | 是否强制归档 |
| `records` | 数组 | 当前项目一条记录 |

**记录字段**：

- 公共字段：`project`、`source`、`archive`、`archive_bytes`、`source_bytes`、`sha256`、`strategy`。
- Git 策略附加：`remote`、`remote_url`、`branch`、`commit`、`upstream`、`verified`。
- 归档策略附加：`fallback_reason`。
- Git 策略的 `archive`、`sha256` 为 `null`，`archive_bytes` 为 `0`。

**格式**：UTF-8、`ensure_ascii=False`、两空格缩进、末尾换行。

**验收判据**：manifest 可解析；每份清单位于对应项目目录；`tool` 为 `proj-janitor`；记录 SHA-256 与归档哈希一致；Git 记录无归档字段值；归档记录保留回退原因；批量运行生成多份项目清单。

**追踪**：`backup.prepare_backup`、`backup.run_backup`；备份测试，包括 `test_batch_run_writes_manifest_per_project` 和 `test_repeated_archives_share_project_directory`。

### 4.14 FR-012 备份 dry-run

**需求描述**：`backup --dry-run` 应展示将创建的项目备份目录、归档路径和每个项目的策略，但不创建目录、归档或 manifest。

**输出**：

- 第一行：`Dry run. Manifest would be: <清单路径>`；多项目时逐行列出各项目清单路径。
- Git 项目：`[git] <项目名>: <脱敏URL> @ <12位提交>`。
- 归档项目：`[archive] <项目名>: <体积> -> <项目目录>/<归档名> (<原因>)`。

**验收判据**：目标目录不存在时 dry-run 后仍不存在；不产生 manifest；输出包含策略与目标路径；退出码反映根处理失败但不因 dry-run 改变。

**追踪**：`cli._cmd_backup`、`backup.prepare_backup`、`backup.run_backup`；`test_dry_run_creates_nothing`、`test_backup_dry_run`、`test_backup_dry_run_shows_git_strategy`。

### 4.15 FR-013 清理规则与计划

**需求描述**：`clean` 应按规则扫描项目内制品，生成包含项目、规则、类型、体积和路径的清理计划。

**规则集合**：

| 规则 | 模式 |
| --- | --- |
| `python-cache` | `__pycache__`、`.pytest_cache`、`.mypy_cache`、`.ruff_cache`、`*.pyc`、`.coverage`、`htmlcov` |
| `python-env` | `.venv`、`venv`、`.tox`、`.nox`、`*.egg-info` |
| `node` | `node_modules`、`.next`、`.nuxt`、`.svelte-kit`、`.turbo`、`.parcel-cache`、`coverage` |
| `build` | `build`、`dist`、`out`、`target`、`CMakeFiles`、`.gradle` |
| `editor` | `.cache`、`.DS_Store`、`Thumbs.db` |

**规则**：

1. 默认使用全部规则；`--rules` 用逗号分隔，只使用指定规则。
2. 遍历不跟随符号链接；跳过 `.git` 目录和符号链接。
3. 匹配目录时整棵目录作为一个动作；匹配文件时作为文件动作。
4. 计划按项目路径、目标路径字符串排序。
5. 体积为匹配对象的表面字节数之和，不等于磁盘实际释放量。
6. 默认仅预览；无动作时输出 `Nothing to clean.`。

**验收判据**：夹具中的 `node_modules`、`__pycache__`、`dist` 被计划删除；源码与 `.git` 不在计划中；未知规则报错；空计划输出固定文本。

**追踪**：`config.ARTIFACT_RULES`、`cleaner.build_cleanup_plan`、`cleaner.resolve_rules`；`test_plan_finds_artifacts_and_protects_sources`、`test_rule_selection`。

### 4.16 FR-014 规则筛选与列表

**需求描述**：用户应能查看全部规则，或仅启用指定规则。

**规则**：

- `--list-rules` 输出 `规则名: 模式1, 模式2, ...`，每行一个规则。
- `--list-rules` 当前仍要求提供 `ROOT` 参数；推荐形式为 `projjan clean ROOT --list-rules`。
- `--rules` 为空或只含空白时，argparse 报错 `at least one rule is required`。
- 未知规则报错 `unknown rule(s): ...; available: ...`，该项目不产生清理动作，CLI 退出码为 `1`。

**验收判据**：规则列表与配置一致；指定单一规则时只产生该类动作；未知规则返回非零并输出可用规则。

**追踪**：`cli._rule_list`、`cleaner.resolve_rules`、`cleaner.format_rules`；`test_list_rules`、`test_rule_selection`。

### 4.17 FR-015 安全删除与确认

**需求描述**：删除必须显式启用，并在交互或 `--yes` 确认后执行。

**规则**：

1. 未指定 `--apply` 时只预览，并提示 `Dry run. Re-run with --apply to delete these items.`。
2. 指定 `--apply` 且存在动作时：
   - 非交互式标准输入且未加 `--yes`：输出 `error: refusing to delete without --yes in a non-interactive session`，返回 `2`；
   - 交互式：询问 `Delete <n> item(s)? [y/N]`，仅 `y` 或 `yes` 继续，否则输出 `Aborted.` 并返回 `2`。
3. 实际删除仅针对计划中的路径；目录使用递归删除，文件使用单文件删除。
4. 删除成功后才累计数量与释放字节；删除失败记录错误，继续处理其他动作。
5. 有删除错误时返回 `1`。

**验收判据**：默认不删除；非交互式未加 `--yes` 拒绝；`--apply --yes` 删除计划项；重复执行幂等；删除失败不导致程序崩溃。

**追踪**：`cli._cmd_clean`、`cleaner.apply_cleanup`、`cleaner.CleanupResult`；`test_clean_defaults_to_dry_run`、`test_clean_requires_confirmation_when_not_tty`、`test_clean_apply_with_yes`、`test_apply_cleanup_removes_only_planned_items`、`test_apply_is_idempotent`。

### 4.18 FR-016 符号链接、根目录与 `.git` 保护

**需求描述**：清理不得删除项目根本身、计划根之外的路径、`.git` 目录或通过符号链接逃逸的目标。

**规则**：

1. 计划阶段跳过项目内的 `.git` 目录和符号链接。
2. 执行阶段再次校验：目标等于项目根或不在项目根内时拒绝，错误为 `target escapes project root`。
3. 目标是符号链接时拒绝，错误为 `refusing to follow symlink`。
4. 校验失败只记录错误，不执行删除。

**验收判据**：符号链接不被跟随、不被删除；`.git` 不在计划中；构造越界目标时执行阶段拒绝；源码目录不被误删。

**追踪**：`cleaner.build_cleanup_plan`、`cleaner.apply_cleanup`；`test_symlink_is_not_followed`、`test_plan_finds_artifacts_and_protects_sources`。

### 4.19 FR-017 退出码、帮助与错误输出

**需求描述**：CLI 应提供统一帮助、版本和退出码，错误信息输出到标准错误。

**规则**：

- `projjan --help`、`projjan <command> --help` 显示用法；缺少子命令或参数错误由 argparse 返回 `2`。
- `projjan --version` 输出 `projjan 0.1.0`。
- 成功为 `0`；部分根失败、备份无项目、目标不是目录、清理或恢复动作失败为 `1`；拒绝删除或确认失败为 `2`。
- 根错误、目标目录错误、确认拒绝等错误输出到标准错误；正常数据和摘要输出到标准输出。
- `scan`/`clean`/`restore` 支持 `--json`；`backup` 不支持 JSON。
- `restore` 的 `--json` 输出纯 JSON，不混入人类提示。

**验收判据**：版本字符串正确；缺少根参数返回 `2`；不存在根返回 `1`；非交互删除返回 `2`；帮助包含四个子命令；`restore --json` 可被严格 JSON 解析。

**追踪**：`cli.main`、`cli.build_parser`、`cli._cmd_scan`、`cli._cmd_backup`、`cli._cmd_restore`、`cli._cmd_clean`；TC-87 自动验证 Python/Rust 的 `--help` 和 `--version` 入口。

### 4.20 FR-018 manifest 恢复

**需求描述**：`restore` 应读取 schema v2 manifest，按记录恢复 Git 或归档项目。省略 `--dest` 时恢复到 manifest 记录的原始 `source`；指定 `--dest` 时恢复到 `--dest/<项目名>/`。两种模式都拒绝覆盖已有目标。

**命令形式**：

```bash
projjan restore MANIFEST [--dest DIR] [--project NAME]
                   [--dry-run] [--no-verify] [--yes] [--json]
```

**规则**：

1. manifest 根必须是 JSON 对象，`schema_version` 必须为 `2`，`records` 必须是非空对象数组。
2. 项目名不能是绝对路径、包含 `/`、`\`、`..` 或 NUL；同名项目不能重复。
3. 省略 `--dest` 时，每条记录的 `source` 必须是绝对路径，不能包含 NUL 或 `..`，文件名必须等于项目名，且不能是文件系统根；父目录存在时必须是目录。
4. 指定 `--dest` 时，目标为 `--dest/<项目名>/`；`--dest` 存在但不是目录时拒绝。
5. 同一批恢复中目标路径不能重复；目标已存在或是符号链接时拒绝恢复，不覆盖、不合并。
6. `git` 策略校验远程 URL 和提交格式，执行 `git clone --no-checkout`，再 `git checkout --detach <commit>`；按 `.gitmodules` 逐层初始化子模块并检出 gitlink 固定提交；含 LFS 属性时在临时仓库安装本地 filter 并执行 `git lfs pull`。全部成功且路径仍位于临时项目目录内后，才移动至目标目录。子模块 URL 不受支持、提交/LFS 对象不可获取或嵌套超过 32 层时失败并清理临时目录。
7. `archive` 策略默认校验 manifest 中的 SHA-256；校验通过后解压至临时目录，要求顶层目录等于项目名，拒绝绝对路径、`..`、特殊文件和越界链接，再移动至目标目录。
8. `--no-verify` 跳过归档 SHA-256 校验；`--project` 可重复指定，只恢复选中项目；`--dry-run` 只输出计划；`--json` 输出纯 JSON。
9. 原始位置模式默认要求交互确认；标准输入不是 TTY 时必须提供 `--yes`；`--json` 的实际恢复也必须提供 `--yes`。用户拒绝或 EOF 时返回 2，不写文件。
10. 多项目恢复中途失败时不回滚已完成项目。

**验收判据**：归档恢复后源码内容正确且排除制品；哈希不匹配、路径穿越、已有目标目录、非法 `source` 和重复目标均被拒绝；Git 恢复为 detached HEAD 且 HEAD 等于 manifest 提交，子模块检出 gitlink 指定提交；原始位置模式在非交互/JSON 场景未给 `--yes` 时拒绝执行；失败后临时目录被清理。

**追踪**：`restore.restore_from_manifest`、`restore.plan_restore`、`restore.execute_restore`、`restore._record_source`、`restore._restore_git`、`restore._restore_submodules`、`restore._restore_lfs`、`restore._restore_archive`、`restore._safe_extract`；`tests/test_restore.py` 与 CLI 恢复测试，含 TC-93～TC-94。

### 4.21 FR-019 备份目标配置与参数命名

**需求描述**：备份操作使用明确的 `backup_dest` 名称，与 `restore` 的 `dest` 区分。CLI 支持 `--backup-dest`，省略时读取 `BACKUP_DEST`；显式 CLI 参数优先。Python API `prepare_backup()` 和 `run_backup()` 使用必填参数 `backup_dest`。备份命令和 API 不接受旧的 `dest` 参数。

**验收判据**：设置 `BACKUP_DEST` 后省略 `--backup-dest` 可将备份写入环境变量指定目录；显式 `--backup-dest` 覆盖环境变量；两者都缺失时 CLI 返回用法错误 `2`；备份 CLI 拒绝 `--dest`；Python 备份 API 只接受 `backup_dest`；`restore --dest` 行为保持不变。

**追踪**：`cli.build_parser`、`cli._cmd_backup`、`backup.prepare_backup`、`backup.run_backup`；`test_backup_uses_backup_dest_environment_variable`、`test_backup_dest_option_overrides_environment_variable`、`test_backup_destination_is_required_without_environment_variable`、`test_backup_dest_option_rejects_legacy_dest`、`test_backup_api_names_destination_backup_dest`、`test_backup_api_rejects_legacy_dest_keyword`。

## 6. 外部接口需求

### 6.1 命令行接口

| 命令 | 用途 | 必需参数 | 主要选项 |
| --- | --- | --- | --- |
| `projjan scan` | 扫描并展示项目 | `ROOT...` | `--all`、`--json` |
| `projjan backup` | 备份项目 | `ROOT...`、`--dest` | `--dry-run`、`--include-artifacts`、`--always-archive` |
| `projjan restore` | 按 manifest 恢复项目 | `MANIFEST`、`--dest` | `--project`、`--dry-run`、`--no-verify`、`--json` |
| `projjan clean` | 预览或执行清理 | `ROOT...` | `--rules`、`--apply`、`--yes`、`--json`、`--list-rules` |
| `projjan --version` | 显示版本 | 无 | 无 |

详细参数、输出示例和 JSON 结构见 `05-接口与CLI文档.md`。

### 6.2 文件系统接口

| 接口 | 方向 | 说明 |
| --- | --- | --- |
| 扫描根 | 读 | 读取目录项、文件元数据和 `.git` 状态 |
| 项目目录 | 读 | 统计文件、构建清理计划 |
| 备份目标目录 | 写 | 创建项目目录、归档和 manifest |
| manifest 与归档 | 读 | `restore` 读取清单、校验 SHA-256、读取归档内容 |
| 恢复目标目录 | 写 | 在 `--dest/<项目名>/` 创建恢复结果，不覆盖已有目录 |
| 清理目标 | 删除 | 仅删除计划内的制品路径 |

工具不创建数据库，不写注册表，不修改项目源码，不自动删除备份。

### 6.3 数据接口

- manifest 为 UTF-8 JSON，按项目写入 `manifest-<时间戳>.json`，结构见 FR-011。
- `scan --json` 和 `clean --json` 输出 JSON 数组；`restore --json` 输出包含 `dry_run` 和 `projects` 的对象。
- 工具不提供 HTTP、gRPC、消息队列或其他网络服务 API；网络访问仅用于 URL-only 的远程 tag 查询和 `restore` 的 Git 克隆。

### 6.4 退出码接口

| 退出码 | 含义 |
| --- | --- |
| `0` | 成功 |
| `1` | 根处理失败、备份无项目、目标不是目录、清理动作失败、manifest/归档无效、SHA-256 不匹配、恢复目标已存在或 Git 恢复失败 |
| `2` | 参数错误、缺少确认、用户拒绝删除 |

## 7. 数据需求

### 7.1 输入数据

- 一个或多个本地目录路径。
- 目录中的项目标记、常规文件元数据、Git 元数据。
- 用户指定的备份目标目录和清理规则。

### 7.2 输出数据

| 数据 | 产生条件 | 保留方式 |
| --- | --- | --- |
| 标准输出文本/JSON | 每次命令 | 由用户或终端决定 |
| 项目备份目录 | `backup` 非 dry-run | `--dest/<项目名>/`，不自动清理 |
| `tar.gz` 归档 | 归档策略 | 位于项目备份目录，不自动清理 |
| `manifest-<时间戳>.json` | 实际备份 | 位于项目备份目录，不自动清理 |
| 恢复的项目目录 | `restore` 非 dry-run | 位于 `--dest/<项目名>/`，不覆盖已有目录 |
| 恢复计划/结果 JSON | `restore --json` | 输出到标准输出，不持久化 |
| 删除结果 | `clean --apply` | 仅终端摘要，无持久日志 |

### 7.3 数据质量与边界

- 体积为常规文件表面字节数，不含目录项、扩展属性、稀疏文件实际占用和硬链接去重。
- 修改时间为带时区偏移的本地时间，精度取决于文件系统。
- 清理“可释放体积”为计划对象表面大小之和，不等于实际磁盘释放量。
- 归档不包含被排除的制品；包含 `.git`；不保证可移植到不同 Git 版本。
- 工具不读取文件内容，因此无法识别归档中的密钥、令牌或个人数据。

### 7.4 数据安全与保留

- 备份目录可能包含完整源码和 `.git` 历史，使用者应自行设置权限、加密和保留期。
- 工具不自动删除旧备份，不提供保留策略或配额管理。
- 清理只删除规则匹配的制品，不删除源码、`.git` 或项目根。
- URL-only 策略允许 HTTPS GitHub URL 内嵌 PAT，但 manifest 和 CLI 输出只保存脱敏后的 URL；归档仍会包含 `.git/config`，因此归档本身可能保留凭据，必须限制访问或先清理远程 URL。
- `restore` 默认校验归档 SHA-256、拒绝覆盖已有目录，并对归档路径和链接做安全校验；Git 恢复不联网预检远程提交是否存在。
- 工具不读取普通源码文件内容，因此无法识别归档或源码中的密钥、令牌和个人数据。

## 8. 范围排除

以下内容不属于 `v0.1.0` 结项基线加 post-v0.1.0 变更的当前需求范围：

- 增量备份、去重、压缩策略选择、加密和远程对象存储；
- 定时任务、守护进程、监控告警和集中管理平台；
- 图形界面、Web 界面和 HTTP API；

- 除 Git 状态读取、远程 tag 查询和 `restore` 的 clone/checkout 外的版本控制操作；

- 对所有 Windows/macOS 版本、网络文件系统和企业 ACL 的完整兼容性保证；当前只声明 CI 覆盖到的具体平台/版本；
