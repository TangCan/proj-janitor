## 2. 设计目标与原则

### 2.1 设计目标

`proj_janitor` 面向本地多项目工作区，提供四个相互独立但共享数据模型的命令：

1. `scan`：发现直接子项目，统计体积和最近修改时间，读取 Git 分支与工作区状态。
2. `backup`：根据 Git 可恢复性选择“仅记录 Git 位置”或创建 `tar.gz` 归档，并按项目生成备份清单。
3. `restore`：读取备份清单，通过 Git 克隆/检出或安全解压归档恢复项目。
4. `clean`：按预定义规则生成清理计划；默认只预览，显式确认后才删除构建和依赖产物。

设计重点不是提供通用文件管理器，而是在“可解释、可审计、默认不破坏”的前提下完成日常项目盘点、备份、恢复和空间回收。

### 2.2 设计原则

| 原则 | 设计体现 |
| --- | --- |
| 安全优先 | 清理默认 dry-run；删除前要求 `--apply` 和确认；保护 `.git`、符号链接和项目根目录边界。 |
| 保守判定 | Git 可恢复性必须通过多项检查；本地 tag 还必须与远程同名 tag 指向同一对象；任一检查失败都回退到归档。 |
| 本地优先 | 不启动监听端口或服务端组件；网络访问仅通过 `git ls-remote` 校验远程 tag，以及 `restore` 的 Git 克隆。 |
| 可审计 | 扫描、清理和恢复支持 JSON；备份按项目生成 `manifest-<时间戳>.json`，归档记录包含大小和 SHA-256。 |
| 简单可部署 | 仅使用 Python 标准库，无运行时第三方依赖；单进程、单命令完成操作。 |
| 数据与视图分离 | `models.py` 定义不可变数据对象；CLI 负责参数和输出，业务模块负责计算。 |
| 失败可见 | 文件系统错误输出到标准错误，并通过退出码反映部分失败或使用错误。 |
| 边界明确 | 只扫描根目录的直接子项目，不递归发现嵌套项目；不提供独立校验、加密、增量备份和远程上传。 |

### 2.3 设计约束

- 运行环境为 Python 3.10 及以上；开发和自测使用 Python 3.12.3。
- 仅保证当前 Linux 环境下的行为；Windows 和 macOS 未做正式验证。
- Git 相关能力依赖本机可执行的 `git`；单个 Git 命令超时时间为 10 秒。
- 不引入数据库、Web 框架、任务队列或后台服务。
- 备份归档格式固定为 `tar.gz`；归档内容包含项目目录及 `.git`，仅按 artifact 规则排除特定产物。
- 清理规则由 `config.py` 静态定义，当前仍不支持配置文件或自定义规则文件。
- URL-only 判定在存在本地 tag 时会查询远程 tag 引用；无本地 tag 时不发起网络查询。
- `restore` 的 Git 策略需要本机 `git` 和可用凭据；归档策略需要可读归档及 manifest 中的 SHA-256。

### 2.4 设计非目标

以下内容不属于当前设计范围：

- 独立归档校验命令（SHA-256 校验已内置于 `restore`）；
- 恢复覆盖已有目录、批量恢复回滚、断点续传和远程提交预检；
- 增量备份、去重、压缩策略选择、加密和远程对象存储；
- 定时任务、守护进程、GUI、HTTP API；
- Git LFS、submodule、tag 和 detached HEAD 的完整备份；
- 对项目内容进行秘密扫描、恶意代码扫描或合规审查；
- 跨平台路径语义和 Windows 文件占用行为的完整适配。

## 3. 系统架构

### 3.1 架构概览

系统采用单进程、分层调用的 CLI 架构。入口层解析命令并组织输出，业务层完成扫描、备份、恢复和清理，数据层提供不可变数据对象与静态配置，外部依赖为本地文件系统、Git 命令和归档文件。

```text
+--------------------------------------+
| 用户 / 自动化脚本                    |
| projjan scan|backup|restore|clean    |
+------------------+-------------------+
                   |
                   v
+--------------------------------------+
| 入口层 cli.py                        |
| argparse、交互确认、退出码            |
| 文本/JSON 输出                       |
+----+-------------+-------------+------+
     |             |             |
     v             v             v
+----------+  +----------+  +----------+
| scanner  |  | backup   |  | restore  |
| 项目发现 |  | 策略选择 |  | 清单校验 |
| Git 状态 |  | tar.gz   |  | Git/解压 |
| 可恢复性 |  | manifest |  | 安全恢复 |
+----+-----+  +----+-----+  +----+-----+
     |             |             |
     |             +------+------+
     |                    |
     v                    v
+------------------+  +------------------+
| cleaner.py       |  | models/config    |
| 规则匹配、安全删除|  | dataclass、规则  |
+--------+---------+  +--------+---------+
         |                     |
         +----------+----------+
                    v
+--------------------------------------+
| 本地资源                             |
| 文件系统、.git、git 命令、tar.gz      |
+--------------------------------------+
```

### 3.2 分层职责

| 层次 | 主要文件 | 职责 | 不负责 |
| --- | --- | --- | --- |
| 入口层 | `proj_janitor/cli.py` | 参数解析、子命令分发、交互确认、输出、退出码 | 项目判定、归档、删除细节 |
| 业务层 | `scanner.py`、`backup.py`、`restore.py`、`cleaner.py` | 发现与统计、恢复性判定、备份、恢复、清理计划和执行 | 参数语法、最终展示格式 |
| 数据层 | `models.py`、`config.py` | 不可变数据对象、人类可读体积、标记和规则常量 | I/O、命令执行 |
| 外部资源 | 文件系统、Git、tarfile | 提供项目内容、Git 元数据、归档能力 | 业务策略 |

### 3.3 依赖方向

- `cli.py` 依赖 `scanner.py`、`backup.py`、`restore.py`、`cleaner.py`、`models.py`。
- `backup.py` 依赖 `scanner.inspect_git_recoverability`、`config.artifact_patterns`、`models.py`。
- `restore.py` 依赖 `backup.sha256_file`、`models.py`，并调用外部 `git` 和 `tarfile`。
- `cleaner.py` 依赖 `scanner.measure_tree`、`config.ARTIFACT_RULES`、`models.py`。
- `scanner.py` 依赖 `config.PROJECT_MARKERS`、`models.py` 和标准库 `subprocess`。
- `models.py`、`config.py` 不反向依赖业务模块，避免循环依赖。

该依赖结构没有插件机制和运行时注册表，模块关系在导入时固定，便于静态审阅。

### 3.4 运行形态

- 安装后入口为 `projjan`，也可通过 `python3 -m proj_janitor` 运行。
- 每次调用执行一个子命令，进程内不保留跨命令状态。
- 扫描结果仅在当前进程内传递给备份或清理逻辑；跨运行状态存在于备份目录、manifest 和恢复目标目录中。
- 不使用线程池或异步任务；目录遍历、Git 调用、归档和恢复均顺序执行。
- 不启动监听端口或服务端组件；网络访问仅通过 `git ls-remote` 和 `restore` 的 `git clone` 子进程完成。

## 4. 模块划分

### 4.1 模块总览

### 4.2 扫描模块

`discover_projects(root, include_unmarked=False)` 的规则如下：

1. 根路径不存在时抛出 `FileNotFoundError("root does not exist: ...")`。
2. 根路径不是目录时抛出 `NotADirectoryError("root is not a directory: ...")`。
3. 若根目录自身包含任一项目标记，则只返回根目录这一个项目。
4. 否则只遍历根目录的直接子目录，不递归。
5. 跳过名称以 `.` 开头的目录、符号链接和空目录。
6. 默认只保留含项目标记的目录；`include_unmarked=True` 时保留所有合格子目录。
7. 项目按目录枚举顺序返回，CLI 收集阶段再按解析后的真实路径去重。

`scan_project(path)` 组合项目名称、标记、体积、最近修改时间和 Git 状态。体积通过 `os.walk(..., followlinks=False)` 统计普通文件大小，遇到符号链接目录不跟随；最近修改时间取所有普通文件 `st_mtime` 的最大值，并转换为本地 `datetime`。

`read_git_state(path)` 只在存在 `.git` 时读取分支和 porcelain 状态。它用于展示，不等同于“可恢复性判定”；即使工作区脏，项目仍可被扫描和展示。

`inspect_git_recoverability(project, patterns)` 是备份策略的核心判定函数，详见第 7 章。

### 4.3 备份模块

`prepare_backup` 负责生成纯计划，不创建目录、不写归档：

- 归一化目标目录：`expanduser().resolve()`；
- 为每个项目分配稳定的 `DEST/<项目名>/` 目录，同名项目追加 8 位路径哈希；
- 计算本次 artifact 排除模式；
- 为每个项目选择 `git` 或 `archive` 策略；
- 为归档项目分配不会冲突的 `<项目名>-YYYYmmdd-HHMMSS.tar.gz` 文件名；
- 为每个项目生成 `manifest-YYYYmmdd-HHMMSS.json` 路径，并处理同一秒内的 `-2`、`-3` 后缀；
- 返回 `(manifest_paths, plans)`，供 dry-run 展示或实际执行。

`run_backup` 在非 dry-run 时创建项目目录，遍历计划并按项目写 manifest。Git 策略只记录远端和提交信息，不下载或上传任何内容；归档策略调用 `backup_project`，清单与归档放在同一项目目录。当前实现按项目隔离可恢复的文件/归档错误、清理部分输出并继续处理其他项目；失败项由 CLI 报告并令进程返回非零码。备份根目录由 `backup_dest` API 参数或 CLI `--backup-dest`/`BACKUP_DEST` 提供。

`backup_project` 使用 `tarfile.open(archive, "w:gz")`，以项目目录名为归档顶层目录，应用文件名/目录名级别的 artifact 过滤，最后计算归档大小和 SHA-256。

### 4.4 清理模块

`build_cleanup_plan(project, rule_names)` 的流程：

1. 解析项目真实路径和规则集合。
2. 将规则展开为 `(规则名, glob 模式)` 列表。
3. 使用 `os.walk(..., followlinks=False)` 遍历。
4. 跳过 `.git` 目录和符号链接。
5. 目录名命中规则时记录为 `dir`，并从后续遍历中剪枝，避免重复统计。
6. 文件名命中规则时记录为 `file`。
7. 按项目路径和条目的字符串路径排序，保证输出稳定。

`apply_cleanup(actions)` 在执行时再次做安全校验，而不是完全信任计划：

- 解析后的目标必须位于项目根目录内部且不能等于项目根；
- 目标本身不能是符号链接；
- 目录使用 `shutil.rmtree`，普通文件使用 `unlink`；
- 目标在执行前已消失时跳过，不记为成功；
- `OSError` 和路径校验 `ValueError` 记录为错误，继续处理后续条目；
- 只有成功删除的条目才累加数量和释放字节数。

### 4.5 CLI 模块

`build_parser` 定义 `scan`、`backup`、`restore`、`verify`、`clean` 五个子命令和顶层 `--version`。`main` 负责捕获 `argparse` 的 `SystemExit` 并转换为整数退出码。

CLI 只做编排，不复制业务算法。它负责：

- 将 argparse 的结果转换为 `Path`；
- 调用 `_collect_projects` 统一处理多根目录和部分失败；
- 在 JSON 与文本输出之间选择；
- 在非交互环境拒绝无 `--yes` 的删除；
- 在 `restore` 中区分 dry-run 计划与实际结果，并输出纯 JSON；
- 将业务异常转换为用户可读错误和退出码。

### 4.6 数据与配置模块

`models.py` 中的对象均为 `@dataclass(frozen=True)`，用于降低跨模块意外修改状态的风险。`BackupPlan` 保存策略选择结果，`BackupRecord` 保存可写入 manifest 的最终记录，两者分离使 dry-run 不产生记录。`RestorePlan` 保存目标、策略、归档或 Git 信息及校验状态，`RestoreResult` 只记录已完成的恢复。

`config.py` 将项目标记和清理规则集中为常量，避免扫描逻辑和清理逻辑各自维护列表。`artifact_patterns(include_artifacts=True)` 返回空元组，表示归档时不排除任何 artifact；该语义与“备份所有内容”一致。

## 5. 关键流程设计

### 5.1 扫描流程

```text
解析 scan 参数
  -> 对每个 ROOT 调用 discover_projects
     -> 根不存在/非目录：记录失败，继续其他 ROOT
     -> 根自身是项目：只产出根项目
     -> 否则枚举直接子目录并过滤
  -> 按真实路径去重
  -> 对每个项目 scan_project
     -> 统计体积和最近修改时间
     -> 读取 Git 分支/状态（可选）
  -> 文本表格或 JSON 输出
  -> 有失败返回 1，否则返回 0
```

设计要点：

- 多根目录中的单个失败不会阻止其他根目录扫描。
- 去重使用 `Path.resolve()` 后的路径，避免同一项目通过不同根重复出现。
- 扫描不修改文件，不执行项目代码。

### 5.2 备份流程

```text
解析 backup 参数
  -> 发现并去重项目
  -> prepare_backup
     -> 为每个项目分配 DEST/<项目名>/ 目录和 manifest 路径
     -> 对每个项目：
        include_artifacts -> archive(include_artifacts)
        always_archive    -> archive(always_archive)
        否则 -> inspect_git_recoverability
                 合格 -> git
                 不合格 -> archive(原因)
  -> dry-run：打印每个项目的清单路径和策略，不创建目录
  -> 实际执行：
     -> 创建各项目目录
     -> git：写 BackupRecord，不产生归档
     -> archive：创建 tar.gz，计算大小和 SHA-256
     -> 每个项目写自己的 manifest-...json
  -> 汇总输出，按失败情况返回退出码
```

### 5.3 恢复流程

```text
解析 restore 参数
  -> load_manifest：校验 schema_version=2 和 records 非空
  -> 解析 --project 过滤；校验项目名和策略
  -> 目标选择：
     -> 指定 --dest：目标 = DEST/<项目名>/；DEST 存在时必须是目录
     -> 省略 --dest：校验 source 为绝对路径、无 ..、文件名等于项目名
        -> 目标 = source 的规范化路径
  -> 检查目标重复；目标已存在/为符号链接则拒绝
  -> git 策略：校验 URL/提交格式
  -> archive 策略：定位归档；默认校验 SHA-256
  -> --dry-run：输出计划（文本或 JSON），不写文件
  -> 原始位置模式且未给 --yes：
     -> 非 TTY 或 --json：拒绝，返回 2
     -> TTY：列出目标并确认；拒绝/EOF 返回 2
  -> 实际执行：
     -> 创建目标父目录
     -> git：clone --no-checkout + checkout --detach + HEAD 校验
     -> archive：临时目录安全解压 + 顶层目录校验
     -> 移动到目标；目标已存在则拒绝
  -> 输出结果；任一项失败返回 1，已恢复项目不回滚
```

### 5.4 清理流程

```text
解析 clean 参数
  -> --list-rules：打印规则后返回（仍需提供 ROOT）
  -> 发现项目
  -> 对每个项目 build_cleanup_plan
  -> 输出 JSON 或文本计划
  -> 未指定 --apply：提示 dry-run 后返回
  -> 无计划：直接返回
  -> 未指定 --yes 且非 TTY：拒绝并返回 2
  -> 未指定 --yes 且为 TTY：输入确认
  -> apply_cleanup
  -> 输出删除数量、释放空间和错误
  -> 有项目级错误或删除错误返回 1
```

清理默认行为是只读预览。即使 `--apply` 已给出，非交互环境仍要求 `--yes`，以避免自动化脚本误删。

### 5.5 URL-only 可恢复性流程

```text
.git 存在？
  -> 否：not a git repository
  -> 是：读取 symbolic-ref HEAD
     -> 失败：detached HEAD
  -> git status --porcelain --untracked-files=all
     -> 失败：git status failed
     -> 非空：working tree is not clean
  -> git stash list
     -> 失败：cannot inspect stashes
     -> 非空：stash entries are not included
  -> branch.<branch>.remote
     -> 空或 "."：branch has no upstream remote
  -> @{upstream}
     -> 空：branch has no upstream
  -> remote get-url
     -> 空：remote URL is unavailable
     -> 非受支持 GitHub URL：remote is not a supported GitHub URL
  -> merge-base --is-ancestor HEAD @{upstream}
     -> 失败：HEAD is not contained in upstream
  -> rev-list --count @{upstream}..HEAD
     -> 失败：cannot compare HEAD with upstream
     -> 非 0：HEAD is ahead of upstream
  -> 本地分支 / submodule / LFS / ignored 文件检查
  -> 本地 tag：
     -> 无 tag：跳过远程查询
     -> 有 tag：git ls-remote --tags --refs <remote>
        -> 查询失败：cannot verify local tags on remote
        -> 本地 tag 不存在于远程：local tag is not pushed: <name>
        -> 同名 tag 对象不一致：local tag differs from remote: <name>
  -> 全部通过：eligible，verified="local-ref"
```

该流程的“可恢复”含义是：根据本地 Git 元数据和远程 tag 引用，当前提交、所有本地分支和本地 tag 看起来已经存在于远端。它不访问 GitHub API，不拉取远端对象，也不能证明远端仓库仍然存在或可访问。存在本地 tag 时会额外执行 `git ls-remote`；无 tag 时不发起网络查询。

### 5.6 归档与 manifest 流程

```text
创建项目目录 DEST/<项目名>/
  -> 对每个归档计划：
     -> 选择唯一归档名 <项目名>-YYYYmmdd-HHMMSS.tar.gz
     -> tarfile w:gz，arcname=项目名
     -> 应用 artifact 过滤器
     -> stat 归档大小
     -> 分块计算 SHA-256
  -> 构造该项目 manifest（schema_version=2，单条 record）
  -> 写 UTF-8 JSON，缩进 2，末尾换行
  -> 多个项目分别写各自的 manifest
```

manifest 是单项目的审计清单，不是数据库，也不是可恢复性证明。若归档创建失败，该项目 manifest 可能不存在；若 manifest 写入失败，归档可能已存在但缺少清单。`restore` 读取 manifest 并据此重建项目，但不会验证远程提交是否仍存在。

## 6. 数据模型与序列化设计

### 6.1 核心数据对象

| 数据对象 | 关键字段 | 用途 |
| --- | --- | --- |
| `GitState` | `branch: str \| None`、`dirty: bool \| None` | 扫描展示的 Git 分支和工作区状态。 |
| `Project` | `path`、`name`、`markers`、`size_bytes`、`last_modified`、`git` | 扫描结果和后续业务输入。 |
| `GitRecovery` | `eligible`、`reason`、`remote`、`remote_url`、`branch`、`commit`、`upstream`、`verified` | URL-only 判定结果。 |
| `BackupPlan` | `project`、`archive_name`、`strategy`、`recovery`、`reason` | 备份计划和 dry-run 展示。 |
| `BackupRecord` | 项目、策略、归档、大小、SHA-256、远端、提交、回退原因 | manifest 记录和运行输出。 |
| `RestorePlan` | 项目、策略、目标、归档、远端 URL、提交、SHA-256、校验状态 | 恢复计划和 dry-run 展示。 |
| `RestoreResult` | 项目、策略、目标 | 已完成的恢复结果。 |
| `CleanupAction` | `project`、`path`、`rule`、`kind`、`size_bytes` | 清理计划和执行输入。 |
| `CleanupResult` | `removed`、`freed_bytes`、`errors` | 清理执行结果。 |

`Project.markers` 和 `last_modified` 可能为空/`None`；`GitState` 和 `GitRecovery` 的字段也允许 `None`，调用方必须处理缺失信息。

### 6.2 扫描 JSON

`scan --json` 输出项目对象数组。每个对象包含：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `name` | string | 项目目录名。 |
| `path` | string | 项目路径。 |
| `size_bytes` | integer | 普通文件总字节数。 |
| `last_modified` | string \| null | 带时区偏移的 ISO 8601 本地时间；无文件时为 `null`。 |
| `markers` | string[] | 命中的项目标记。 |
| `git` | object \| null | `{"branch": string\|null, "dirty": bool\|null}`；非 Git 项目为 `null`。 |

空结果输出 `[]`。JSON 使用 UTF-8 文本、`ensure_ascii=False`、缩进 2。

### 6.3 清理 JSON

`clean --json` 输出 `CleanupAction` 数组。每个对象包含：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `project` | string | 项目名。 |
| `path` | string | 待删除条目路径。 |
| `rule` | string | 命中的规则名。 |
| `kind` | string | `dir` 或 `file`。 |
| `size_bytes` | integer | 计划阶段估算的大小。 |

`clean --json` 的 stdout 输出纯 JSON；执行结果提示按 CLI 约定输出，且已由回归用例覆盖（`c4fa6d9`，DEF-001）。

`restore --json` 输出对象：`{"dry_run": bool, "projects": [...]}`。计划模式的项目字段包括 `project`、`strategy`、`target`、`archive`、`remote_url`（脱敏）、`commit`、`sha256`、`sha256_verified`；执行模式只包含 `project`、`strategy`、`target`。该 JSON 为纯 JSON，不混入提示文本。

### 6.4 manifest v2

manifest 文件位于 `DEST/<项目名>/manifest-<时间戳>.json`，每份清单只包含一个项目记录。顶层字段如下：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `schema_version` | integer | 固定为 `2`。 |
| `created_at` | string | UTC ISO 8601 时间。 |
| `tool` | string | 固定为 `proj-janitor`。 |
| `version` | string | 生成该 manifest 的工具版本，当前为 `0.1.0`。 |
| `include_artifacts` | boolean | 是否要求包含被规则排除的产物。 |
| `always_archive` | boolean | 是否强制归档。 |
| `records` | object[] | 每个项目一条记录。 |

记录字段：

| 字段 | Git 策略 | 归档策略 | 说明 |
| --- | --- | --- | --- |
| `project` | 有 | 有 | 项目名。 |
| `source` | 有 | 有 | 源项目路径。 |
| `archive` | `null` | 归档文件路径 | 归档位置。 |
| `archive_bytes` | `0` | 实际大小 | 归档字节数。 |
| `source_bytes` | 有 | 有 | 扫描时的源体积估算。 |
| `sha256` | `null` | 归档摘要 | 归档完整性校验值。 |
| `strategy` | `git` | `archive` | 备份策略。 |
| `remote` | 有 | 无 | Git 远端名。 |
| `remote_url` | 有 | 无 | 远端 URL。 |
| `branch` | 有 | 无 | 当前分支。 |
| `commit` | 有 | 无 | 当前提交。 |
| `upstream` | 有 | 无 | 上游引用。 |
| `verified` | `local-ref` | 无 | 本地引用级验证标记。 |
| `fallback_reason` | 无 | 可能有 | 回退归档的原因。 |

`asdict` 会保留值为 `None` 的字段，因此 manifest 中字段集合稳定，但不同策略的记录会在语义上缺少部分值。

### 6.5 序列化约定

- 时间：扫描使用本地 `datetime.isoformat()`；manifest 使用 `datetime.now(timezone.utc).isoformat()`。
- 路径：直接使用 `str(Path)`，不做相对化或 URL 编码。
- 文本：UTF-8，不转义非 ASCII 字符。
- manifest：缩进 2，末尾换行。
- JSON 输出不包含 schema 版本字段，字段变更需通过版本升级和文档说明管理。
- 不使用 pickle、数据库二进制格式或自定义压缩序列化。

## 7. Git 可恢复性判定设计

### 7.1 判定目的

“URL-only 备份”适用于可以从 GitHub 重新获取的仓库。为了降低数据丢失风险，系统只在本地证据充分时选择该策略；否则创建完整归档。判定默认不执行 `git fetch`；存在本地 tag 时会执行 `git ls-remote --tags --refs` 校验远程 tag。

### 7.2 检查项与失败原因

| 顺序 | 检查 | 通过条件 | 失败原因 |
| --- | --- | --- | --- |
| 1 | `.git` 存在 | 存在 | `not a git repository` |
| 2 | 当前分支 | `symbolic-ref --short HEAD` 成功 | `detached HEAD` |
| 3 | 工作区 | `status --porcelain --untracked-files=all` 成功且为空 | `git status failed` / `working tree is not clean` |
| 4 | stash | `stash list` 成功且为空 | `cannot inspect stashes` / `stash entries are not included` |
| 5 | 分支远端 | `branch.<branch>.remote` 非空且不为 `.` | `branch has no upstream remote` |
| 6 | upstream | `@{upstream}` 可解析 | `branch has no upstream` |
| 7 | 远端 URL | `remote get-url` 成功 | `remote URL is unavailable` |
| 8 | URL 形态 | 仅接受受支持的 GitHub HTTPS/SSH 形式；HTTPS 可内嵌 PAT，持久化前脱敏 | `remote is not a supported GitHub URL` |
| 9 | HEAD | `rev-parse HEAD` 成功 | `HEAD is unavailable` |
| 10 | 提交包含关系 | `merge-base --is-ancestor HEAD @{upstream}` 成功 | `HEAD is not contained in upstream` |
| 11 | 领先提交数 | `rev-list --count @{upstream}..HEAD` 为 0 | `cannot compare HEAD with upstream` / `HEAD is ahead of upstream` |
| 12 | 本地 tag | `tag --list` 成功；无 tag 直接通过；有 tag 时逐项与 `ls-remote --tags --refs` 的同名对象 ID 比较 | `cannot list tags` / `local tag is not pushed: <name>` / `local tag differs from remote: <name>` / `cannot verify local tags on remote` |
| 13 | submodule 文件 | `.gitmodules` 不存在 | `submodules are not supported` |
| 14 | submodule 状态 | `submodule status` 成功且为空 | `cannot inspect submodules` / `submodules are not supported` |
| 15 | LFS 配置 | `.lfsconfig` 不存在 | `Git LFS is not supported` |
| 16 | LFS 属性 | `git grep -l filter=lfs -- '*.gitattributes'` 成功且无输出 | `cannot inspect Git LFS attributes` / `Git LFS is not supported` |
| 17 | 忽略文件 | `ls-files --others --ignored ...` 成功 | `cannot inspect ignored files` |
| 18 | 忽略文件内容 | 每个忽略路径的每一段都匹配 artifact 模式 | `ignored path is not an artifact: X` |
| 19 | 本地分支列表 | `for-each-ref refs/heads` 成功 | `cannot list local branches` |
| 20 | 远端跟踪引用 | 指定远端下存在引用 | `cannot list remote-tracking refs` / `no remote-tracking refs` |
| 21 | 分支推送状态 | 每个本地分支相对所有远端跟踪引用无独有提交 | `cannot inspect local branch: X` / `local branch is not fully pushed: X` |

### 7.3 接受的 GitHub URL

| 形式 | 示例 |
| --- | --- |
| HTTPS | `https://github.com/owner/repo`、`https://github.com/owner/repo.git` |
| 带 PAT 的 HTTPS | `https://token@github.com/owner/repo.git`、`https://user:token@github.com/owner/repo.git`；持久化前脱敏 |
| SSH URL | `ssh://git@github.com/owner/repo`、`ssh://git@github.com:22/owner/repo.git` |
| SCP 风格 | `git@github.com:owner/repo`、`git@github.com:owner/repo.git` |

拒绝 http、非 GitHub 主机、额外路径、查询串、片段、非法端口和非仓库本地路径。owner 和 repository 只允许字母、数字、点、下划线和连字符，且不能为 `.` 或 `..`。HTTPS 凭据仅用于访问私有仓库，不写入 `GitRecovery`、manifest 或 CLI 输出；归档仍可能包含 `.git/config` 中的凭据。

### 7.4 设计限制

- `verified="local-ref"` 只表示本地引用和远程 tag 引用检查通过，不表示远端 HEAD 或提交内容已在本机验证。
- 远端跟踪引用可能过期；系统不执行 fetch，因此不能证明远端当前仍包含该提交。
- 存在本地 tag 时会执行 `git ls-remote --tags --refs` 查询远程；仅本地存在、与远程对象不一致或无法查询的 tag 会阻止 URL-only 策略。
- stash、submodule、LFS 和未按 artifact 规则覆盖的忽略文件仍会阻止 URL-only 策略。
- 判定失败时只记录首个原因；reason 用于解释回退，不是完整诊断报告。
- Git 命令异常被统一转换为 `None`，调用方无法区分“命令不存在”“超时”和“非零退出”的具体底层原因。

## 8. 清理安全设计

### 8.1 规则与匹配

清理规则由 `ARTIFACT_RULES` 定义，使用 `fnmatch` 对目录名或文件名逐段匹配。目录命中后会剪枝，避免对其内部再次生成计划。默认规则包括 Python 缓存/虚拟环境、Node 依赖/框架缓存、构建目录和编辑器临时文件。

多数清理规则按名称匹配；`coverage` 特例在 `c4fa6d9` 收紧为项目根目录且存在覆盖率产物标记时才匹配。其他通用名称仍需通过默认 dry-run 和人工审阅防止误删；项目没有自定义白名单配置。

### 8.2 多层保护

| 保护 | 实现 |
| --- | --- |
| 默认只读 | 未指定 `--apply` 时只输出计划。 |
| 显式执行 | 指定 `--apply` 才进入删除流程。 |
| 交互确认 | TTY 环境询问 `[y/N]`；非 TTY 必须 `--yes`。 |
| 根目录保护 | 目标解析后必须严格位于项目根内部。 |
| `.git` 保护 | 遍历时跳过 `.git`，规则不会进入该目录。 |
| 符号链接保护 | 规划时跳过符号链接；执行时再次拒绝符号链接。 |
| 计划/执行分离 | 先构建 `CleanupAction` 列表，再统一执行。 |
| 部分失败继续 | 单条删除失败记录错误，不中止其余条目。 |
| 结果可核对 | 输出删除数量、释放空间和每个错误。 |

### 8.3 残余风险

- 计划与执行之间存在 TOCTOU（检查后变化）窗口；执行时会重新解析路径并检查符号链接，但不能消除并发替换风险。
- `shutil.rmtree` 删除目录时，目录内部若发生并发变化，结果取决于操作系统和文件系统。
- 释放空间按计划阶段估算，不等于文件系统实际回收量；稀疏文件、硬链接和压缩/去重文件系统可能产生差异。
- 删除是不可逆操作；v0.1.0 不提供回收站、审计日志或撤销。
- 规则可能匹配用户未预期的同名目录；执行前应审阅计划。

## 9. 错误处理与退出码

### 9.1 错误分类

| 类别 | 示例 | 处理方式 |
| --- | --- | --- |
| 参数错误 | 缺少 ROOT、非法规则、未知子命令 | argparse 输出用法并以 2 退出。 |
| 根路径错误 | 根不存在、不是目录 | 输出 `error: ...`，记录失败，继续其他根。 |
| 项目级扫描错误 | 权限不足、目录读取失败 | 记录失败并继续。 |
| Git 命令失败 | 超时、命令不存在、非零退出 | 可恢复性判定失败并回退归档；扫描状态可能为空。 |
| 备份目标错误 | 目标不是目录 | 输出错误并返回 1。 |
| 归档失败 | 磁盘满、权限不足、文件变化 | 当前实现会中止本次备份，可能留下不完整目录。 |
| manifest/归档恢复错误 | 文件不存在、schema 不支持、记录无效、SHA-256 不匹配 | `restore` 输出 `error: ...` 并返回 1；不写入目标目录。 |
| Git 恢复失败 | 远程不可达、提交不存在、认证失败、checkout 失败 | 清理临时目录并返回 1；已恢复的其他项目不回滚。 |
| 清理规则错误 | `unknown rule(s)` | 输出项目级错误并继续其他项目。 |
| 删除失败 | 权限、路径逃逸、符号链接 | 记录错误，继续其他条目，最终返回 1。 |
| 确认拒绝 | 非 TTY 无 `--yes`，或用户回答否 | 返回 2，不删除。 |

### 9.2 退出码

| 退出码 | 含义 |
| --- | --- |
| `0` | 命令成功；或清理 dry-run 无项目级失败。 |
| `1` | 根路径/部分项目失败、无项目可备份、备份目标非法、manifest/归档恢复失败、Git 恢复失败、删除失败。 |
| `2` | 参数/用法错误、未知规则、非交互环境拒绝删除、用户取消确认。 |

`argparse` 自身产生的用法错误由 `main` 捕获 `SystemExit` 并返回其代码，通常为 2。

### 9.3 错误信息设计

- 业务错误以 `error: ` 前缀写入标准错误。
- 扫描表格、dry-run 计划和成功摘要写入标准输出。
- Git 可恢复性失败原因进入备份计划和 manifest 的 `fallback_reason`，不直接作为异常抛出。
- 当前没有结构化错误码、日志级别或错误聚合报告；调用方主要依赖退出码和文本。

## 10. 安全设计

### 10.1 数据与网络安全

- 工具不启动网络服务，不上传项目内容、路径或 Git 信息；仅在 URL-only 的远程 tag 查询和 `restore` 的 Git 克隆时调用外部 `git`。
- 不读取环境变量中的令牌，不调用 GitHub API。
- Git 远端 URL 只从本地配置读取；HTTPS GitHub URL 允许内嵌 PAT，但写入 `GitRecovery`、manifest 和 CLI 输出前会去除 userinfo、查询字符串和片段。
- 归档包含项目文件，可能含密钥、个人数据或内部资料；归档还会包含 `.git/config`，因此内嵌 PAT 可能保留在归档中。工具不做内容扫描或脱敏，使用者必须控制备份目录权限、清理远程 URL 或加密留存。
- `restore` 读取 manifest 和归档，默认校验 SHA-256，并拒绝覆盖已有目标目录；Git 恢复依赖本机凭据配置，不联网预检提交是否存在。
- 输出路径和项目名可能包含敏感信息；日志/工单引用时需脱敏。

### 10.2 文件系统安全

- 扫描不跟随符号链接目录，统计使用 `follow_symlinks=False`。
- 清理计划跳过 `.git` 和符号链接。
- 删除前验证目标在项目根内，防止计划被篡改后删除根外路径。
- 归档使用 `tarfile` 写入；`restore` 读取时先校验 SHA-256，再解压到临时目录，拒绝绝对路径、`..`、特殊文件和越界链接，确认顶层项目目录后移动到目标位置。
- 恢复目标已存在时拒绝覆盖；多项目恢复中途失败时，已恢复项目不回滚，需要人工清理。
- 指定 `--dest` 时写入范围限定在目标父目录；省略 `--dest` 时目标来自 manifest 的 `source`，写入范围由 manifest 决定，因此 CLI 要求交互确认或显式 `--yes`，并应只使用可信 manifest。
- 原始位置模式校验 `source` 为绝对路径、无 `..`/NUL、文件名等于项目名且非文件系统根；跨机器或目录布局变化时不保证路径仍适用。
- 不修改项目源文件；备份只读源项目，清理只删除计划条目。

### 10.3 依赖与供应链

- 运行时仅使用 Python 标准库，减少第三方依赖风险。
- 构建依赖为 `setuptools>=68`，未锁定构建依赖版本。
- 仓库未包含 `LICENSE` 文件，分发前需补充许可信息。
- 外部 `git` 可执行文件由运行环境提供，版本和行为差异不在工具控制范围内。

### 10.4 安全非目标

v0.1.0 不提供认证、授权、多租户隔离、加密存储、密钥管理、审计签名、恶意文件检测和合规证明。项目定位为单用户本地工具，不应直接暴露为多用户服务。

## 11. 性能与容量设计

### 11.1 时间复杂度

| 操作 | 复杂度 | 说明 |
| --- | --- | --- |
| 项目发现 | O(根目录直接子项数) | 不递归发现项目。 |
| 单项目体积统计 | O(项目文件数) | `os.walk` 遍历全部普通文件。 |
| Git 状态 | O(工作区变化量 + Git 进程启动) | 受 Git 实现和仓库规模影响。 |
| URL-only 判定 | O(本地分支数 + 忽略文件数 + Git 进程数) | 多次启动 Git 子进程。 |
| 清理计划 | O(项目文件/目录数) | 目录命中后剪枝。 |
| 归档 | O(归档内容字节数) | 压缩 CPU 和磁盘 I/O 是主要成本。 |
| SHA-256 | O(归档字节数) | 1 MiB 分块读取，内存占用低。 |

### 11.2 内存与磁盘

- 扫描结果按项目数保存在内存中，单个项目仅保存路径、标记、大小和时间，不保存文件清单。
- 清理计划按命中条目数保存在内存中；大型 `node_modules` 可能产生大量条目，但目录命中会剪枝，通常以目录级记录为主。
- 归档采用流式 `tarfile` 写入；SHA-256 采用 1 MiB 分块读取，不将整个归档载入内存。
- 备份至少需要与源项目大小相当的可用磁盘空间；压缩率取决于文件类型。
- 无并发写入协调，多个备份进程可能同时写入同一项目目录，但共享源项目时仍可能读到变化中的文件；同一秒内的文件名冲突通过 `-2`、`-3` 后缀规避。

### 11.3 性能边界

v0.1.0 未建立性能基线，未进行大规模基准测试。已知使用特征包括：

- 全量目录遍历和全量归档，项目越大耗时越长；
- 每个项目的 Git 判定会启动多个 Git 子进程，项目数多时进程开销明显；
- 单个 Git 命令超时 10 秒，超时按失败处理；
- 没有进度条、断点续传、增量归档或并行压缩；
- `restore` 的归档需要完整解压，Git 恢复需要完整克隆，均没有进度条或断点续传；
- 没有文件数、总字节数或运行时间上限。

因此，性能结论只适用于常规本地工作区，不构成 SLA。大目录、网络文件系统、低性能磁盘和高项目数场景应先在测试目录验证。

## 13. 数据库设计说明

### 13.1 数据库选型结论

本项目不适用数据库设计。v0.1.0 不包含关系型数据库、NoSQL 数据库、嵌入式数据库或远程数据服务，也没有数据库连接、表、索引、视图、存储过程、事务和迁移脚本。

原因如下：

- 工具是无状态、单进程、一次性执行的本地 CLI；
- 输入来自文件系统和 Git，输出为终端文本、JSON 或备份目录；
- 不需要跨进程共享状态、并发事务或复杂查询；
- 引入数据库会增加部署、备份和故障面，与最小依赖目标冲突。

### 13.2 持久化替代物

| 持久化对象 | 形式 | 生命周期 | 说明 |
| --- | --- | --- | --- |
| 扫描结果 | 标准输出/JSON | 进程内或调用方保存 | 不作为工具自身状态存储。 |
| 清理计划 | 标准输出/JSON | 进程内 | 不落盘；执行时重新校验路径。 |
| 备份归档 | `tar.gz` 文件 | 由用户保留 | 位于 `DEST/<项目名>/`，包含项目内容和 `.git`。 |
| 备份清单 | `manifest-<时间戳>.json` | 与项目目录共存 | 每份清单一个项目记录，记录策略、路径、大小、SHA-256 和 Git 信息。 |
| 恢复结果 | 项目目录 | 由用户保留 | `restore` 写入 `--dest/<项目名>/`，不覆盖已有目录。 |

manifest 是审计和追溯文件，不是数据库：它没有事务、并发控制、锁、索引、查询接口和迁移机制；写入采用一次性覆盖式 `write_text`，中途失败不会自动回滚。

### 13.3 数据一致性

- 扫描统计与后续备份之间没有快照隔离；源项目变化会导致 `source_bytes` 与实际归档内容不一致。
- 归档 SHA-256 在归档完成后计算，能校验归档文件本身是否被改动，但不校验解压后内容。
- manifest 在全部记录生成后写入；运行中断可能留下“有归档、无清单”或“有部分归档、无清单”的状态。
- 无数据库事务，因此不提供跨项目原子性；不同项目记录可能处于不同完成状态。
- `restore` 在恢复前校验归档 SHA-256；解压和 Git 克隆在临时目录完成后移动到目标目录，单个项目失败会清理临时目录，但多项目批次不回滚已完成项目。
- 无数据保留、归档清理或配额策略；留存由用户负责。

### 13.4 数据安全与隐私

备份可能包含源代码、配置、历史提交、凭据和个人信息。工具不自动排除 `.env`、密钥文件或其他敏感文件，只按 artifact 规则排除构建/依赖产物。使用方应在备份前确认内容范围，并通过目录权限、加密磁盘或外部加密工具保护备份。

### 14.1 关键接口契约

- `prepare_backup` 必须保持“无副作用”，否则 dry-run 语义会被破坏；它按项目返回 manifest 路径和计划。
- `inspect_git_recoverability` 只返回判定结果，不抛出 Git 异常；调用方通过 `eligible` 和 `reason` 决定策略。存在本地 tag 时允许执行 `git ls-remote` 查询远程。
- `BackupPlan.strategy` 只能是 `git` 或 `archive`；`archive_name` 仅归档策略非空。
- `restore_from_manifest` 必须先完成 manifest 校验和归档 SHA-256 校验，再创建目标；目标已存在时拒绝覆盖。`dest=None` 时必须校验记录的 `source`，该模式由 CLI 负责确认或要求 `--yes`。
- `apply_cleanup` 不信任 `CleanupAction` 的路径，必须重新解析并校验。
- CLI 的 JSON 序列化只负责字段投影，不改变业务对象；`restore --json` 不混入人类提示文本。
- 所有跨模块数据对象应保持不可变；需要变更时创建新实例。

## 15. Rust 实现与当前设计补充（2026-10-27）

本节补充 Rust crate `proj-janitor 0.2.3` 与其发布后的 main 修订。原 2–14 章主要描述 Python `0.1.0`，其中对“当前版本/当前平台”的表述仅适用于历史基线；当前源码结构以此节为准。该补充是代码回溯，不代表正式设计评审记录。

### 15.1 Rust 模块结构

| 模块 | 职责 | 关键边界 |
| --- | --- | --- |
| `src/main.rs` | Clap CLI、manifest 数据模型、通用路径与输出工具 | `BACKUP_DEST` 由 Clap env 参数读取；参数错误返回非零 |
| `src/project.rs` | 项目发现、体积/Git 状态、GitHub 可恢复性检查 | Git 命令带超时；清理与备份不跟随项目内部符号链接 |
| `src/backup.rs` | 备份策略、项目目录区分、manifest 写入 | `create_new` 防止覆盖；失败项目隔离；备份目标先做路径校验 |
| `src/archive.rs` | tar.gz 生成/安全解包、哈希、跨平台路径判定 | 拒绝越界、特殊文件、硬链接、冲突组件；临时目录完成后再 rename |
| `src/restore.rs` | manifest 预检、Git 和归档恢复、确认/退出码 | 先验证名称、目标和哈希，再执行；Git 用临时仓库，完成后发布目标 |
| `src/clean.rs` | 白名单规则、清理计划、执行 | 默认 dry-run；删除前重新检查路径边界和符号链接 |
| `src/tests.rs`、`tests/rust_cli.rs` | Rust 单测与 CLI 集成测试 | 使用临时目录和本地 Git fixture |

Python 与 Rust 不是 FFI 绑定，共享的是 CLI 语义和 schema v2 文件格式；`tests/cross_version_compat.py` 验证两种实现之间的归档互操作。

### 15.2 当前备份权限设计

Unix 上新建的备份根目录和每项目目录以 `0700` 创建，归档及 manifest 以 `0600` 原子占名创建；已有目录权限不修改。权限位仍受进程 umask 进一步收紧。Windows 使用目标目录继承的 ACL，不宣称 POSIX 权限位在 Windows 上等价。此保护不加密归档内容，也不脱敏项目文件中的密钥。

### 15.3 当前跨平台路径策略

恢复清单中的项目名在 Git 和 archive 策略前统一按 Windows 可移植组件规则校验，包括保留设备名、非法字符、尾随空格/点和控制字符。Windows 的 DOS 设备别名 `CONIN$`/`CONOUT$` 同样拒绝。归档条目还需通过项目根约束、大小写与 Unicode 规范化冲突检查，目录专属归档以“成员数量”而非“普通文件数量”判空。

### 15.4 数据库与依赖说明

当前 Rust 实现仍无数据库、服务端或外部 API；manifest 和归档是文件系统持久化格式。运行时直接依赖及许可证表达式见 08；Cargo.lock 固定传递依赖版本。元数据检查不等于第三方法律许可审查。
