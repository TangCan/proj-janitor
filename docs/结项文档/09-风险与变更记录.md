### 4.4 重点风险说明

#### R-01 本地单点资产风险

当前没有 Git remote，源码、标签和结项文档只存在于本地工作区。一次磁盘故障、误删或机器丢失就可能同时失去代码、历史和文档。自动化测试不能替代异地副本。

建议：

1. 由项目负责人配置可信远程仓库并推送 `main` 与 `v0.1.0` 标签。
2. 至少保留一份异地或离线副本。
3. 定期用 `git fsck`、`git rev-parse` 和文档哈希校验完整性。
4. 不把唯一副本放在正在被清理的磁盘或项目目录内。

#### R-02 URL-only 的恢复幻觉

URL-only 只验证本地引用和 URL 形式，`verified` 字段为 `local-ref`；工具不会联网确认远程是否仍存在该提交。远程删除、转私有、强制推送、分支保护变化都可能导致记录失效。

建议：

- 对不可替代的项目使用 `--always-archive`，不要只看“已推送”就删除源目录。
- 定期从 manifest 随机抽取记录做 `git clone` + `git checkout` 演练。
- 在交付说明中明确 URL-only 的边界，避免使用者把它理解为“云端已有完整备份”。

#### R-03 清理误删

清理是唯一具有破坏性的功能。默认 dry-run，删除前有根目录/`.git`/符号链接保护；`coverage` 规则已在 `2884075` 收紧到项目根和覆盖率产物标记。其他通用名称仍需人工审阅。

建议：

- 任何 `--apply` 前必须人工审查计划。
- 对 `build`、`dist`、`target`、`out` 等通用名称逐个确认；`coverage` 规则另有产物标记保护。
- 优先使用 `--rules` 明确限定范围。
- 即使 DEF-002 已修复，对真实项目执行 `clean --apply --yes` 前仍须审阅 dry-run 计划。

#### R-05 备份敏感数据

归档默认包含 `.git`，可能包含历史提交中的密钥、`.env`、数据库转储和个人信息；manifest 还可能记录 GitHub URL（通常含组织/仓库名）。工具不做加密、脱敏、访问控制或审计签名。

建议：

- 备份目录使用 `0700` 或更严格权限。
- 在磁盘/归档层加密；不要把密钥和备份放在同一保护域。
- 分享 manifest 或归档前审查 URL、路径和内容。
- 发现凭据泄露时按 07 第 7.7 节处理并轮换凭据。

#### R-14 原始位置恢复的路径信任

省略 `--dest` 时，`restore` 不再把写入限制在用户显式给出的父目录，而是使用 manifest 的 `records[].source`。工具会拒绝缺失、相对路径、包含 `..`、项目名不匹配、重复目标、根目录、已存在目标或符号链接的 `source`，但仍无法判断该路径是否真的是“原来的项目位置”。错误或恶意 manifest 可以把新目录写到任意可写位置；跨机器或不同挂载布局也可能恢复到非预期路径。

建议：

- 只对由本工具生成、且来源可信的 manifest 使用原始位置模式。
- 实际恢复前先 `--dry-run` 审查每个 target；非交互或 `--json` 场景必须显式 `--yes`。
- 跨机器、跨用户或路径布局变化时使用 `--dest`，把写入限制在明确的父目录内。
- 不把原始位置模式用于来源不明的归档或共享 manifest。

### 7.2 回滚策略

代码回滚：

```bash
# 查看代码基线；该提交未打新标签，--exact-match 会失败
git describe --tags 64808df
# 预期类似：v0.1.0-8-g64808df

# 回到 v0.1.0 基线
git checkout v0.1.0

# 如需回到初始实现（不推荐用于生产数据）
git checkout 5cf2a1d
```

回滚注意：

- 代码基线 `64808df` 未打新标签，不能用 `git describe --tags --exact-match` 判断版本。
- 回到 `5cf2a1d` 会失去 URL-only、manifest v2、PAT/tag 规则、按项目目录、`restore` 和原始位置恢复；只应在隔离环境排查问题时使用。
- 代码回滚不会回滚已经生成的备份、manifest 或删除操作；清理没有撤销命令。
- v2 manifest 不能被初始版本正确理解；回滚后不要用旧版本继续写同一备份目录。
- 结项文档已跟踪，但不在 `v0.1.0` 标签内；回滚代码不会回滚文档。
- 旧 `backup-*` 运行目录不会自动迁移；回滚到旧版本后仍按旧布局写入。

数据回滚：

- 优先使用 `projjan restore MANIFEST`（默认回原始位置，需确认或 `--yes`）或 `projjan restore MANIFEST --dest DIR`；Git 策略按 manifest 的 `remote_url` + `commit` 克隆并 detached checkout，archive 策略先校验 SHA-256 再安全解压。
- 手工回退时按 07 手册执行 `git clone`/`git checkout` 或 `tar -xzf`；手工流程不提供哈希校验、路径穿越防护和覆盖保护。
- 如果源目录已被删除且没有归档/远程副本，工具无法恢复；这不是回滚能解决的问题。

当前可接受的残留风险：

- 仅在 Linux x86_64、Python 3.12.3 验证；其他平台/版本不作为支持承诺。
- 无外部验收；结项结论限定为内部自测。
- `restore` 已提供，但不支持覆盖、批量回滚、断点续传和远程提交预检；Git 恢复为 detached HEAD；省略 `--dest` 时信任 manifest 的 `source`。
- 无独立 `verify` 命令；归档 SHA-256 校验已内置于 `restore`。
- 归档包含 `.git`，体积偏大；这是保留仓库元数据的取舍；`.git/config` 可能保留 PAT。
- 无自动保留/加密/去重；由使用者和操作系统承担。

当前不可接受的残留风险：

- 对真实项目清理时仍先检查 dry-run 计划，并检查批量备份命令的退出码及失败摘要。
- 把 URL-only 记录当作唯一备份后删除源目录。
- 使用来源不明或被篡改的 manifest 执行原地恢复。
- 在没有异地副本的情况下声称项目资产已安全归档。

上述“不可接受”项不表示项目不能结项，而表示使用范围必须受限，或在扩大使用前完成对应修复。
