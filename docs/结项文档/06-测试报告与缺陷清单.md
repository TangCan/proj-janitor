## 4. 测试策略与范围

### 4.1 测试层次

| 层次 | 对象 | 方法 |
| --- | --- | --- |
| 模块测试 | `scanner.py`、`backup.py`、`restore.py`、`cleaner.py` | 直接调用函数，断言返回值、文件和目录副作用 |
| CLI 集成测试 | `cli.main()` | 传入参数列表，重定向 stdout/stderr，断言退出码与输出 |
| 冒烟测试 | 已安装命令/真实样本目录 | 扫描、dry-run、wheel 安装后执行 `--version` 与 `scan --json` |
| 静态复核 | 源码与文档 | 代码审查确认异常路径、输出契约和需求一致性 |

### 4.2 测试方法

- **真实文件系统**：不使用 mock 文件系统，直接验证文件创建、删除、归档内容和符号链接行为。
- **真实 Git**：使用本地 Git 仓库和裸仓库构造 clean、dirty、stash、未推送、非 GitHub 远程等状态。
- **行为断言**：优先断言用户可见结果（退出码、stdout/stderr、文件是否存在、manifest 字段），而不是内部实现细节。
- **子测试**：URL 校验使用 `subTest` 分别覆盖 4 个接受样例和 10 个拒绝样例。
- **无重试**：测试不包含自动重试；一次失败即视为失败。
- **串行执行**：`unittest discover` 默认串行执行，不验证并发安全。
- **故障注入有限**：仅在结项复核中手工构造了归档权限拒绝场景，未建立系统化故障注入套件。

3. 未在临时目录之外产生文件修改。
4. 该删除的条目已删除，该保留的源码、`.git` 和外部符号链接目标仍然存在。

### 7.3 覆盖结论与缺口

- 19 项 FR 均有至少一个自动化用例或冒烟证据，没有完全未触及的功能需求。
- 6 项 FR 为部分覆盖，主要缺口是标记矩阵、修改时间、文本输出、重叠根去重和帮助/异常路径。

#### DEF-001 `clean --json` 输出混入人类可读文本

| 项目 | 内容 |
| --- | --- |
| 等级 | 中 |
| 状态 | 已修复（`c4fa6d9`；回归：`test_clean_json_is_pure`, `test_clean_json_apply_is_pure`） |
| 发现方式 | 运行时复现 |
| 影响需求 | FR-017 的输出一致性、03 第 6.3 节数据接口约定；`05-接口与CLI文档.md` 中 `clean --json` 契约 |
| 影响范围 | 所有使用 `clean --json` 的脚本和自动化流程 |

**现象**：`projjan clean <ROOT> --json` 先输出合法 JSON 数组，随后在 stdout 追加 `Dry run. Re-run with --apply to delete these items.`；加 `--apply --yes` 时追加 `Removed N item(s), freed ...`。严格 JSON 解析器会报 `Extra data`。

**证据**：

```bash
projjan clean "$TMP/app" --json > clean.json
python3 -c 'import json; json.load(open("clean.json"))'
# json.decoder.JSONDecodeError: Extra data: line 17 column 1
```

复现中命令退出码为 0，JSON 本身有效，但尾部多出提示行。TC-29 只验证了 `scan --json`，未覆盖 `clean --json`，因此该缺陷未被现有测试发现。

**根因**：`cli._cmd_clean` 在输出 JSON 后没有提前返回，继续执行 dry-run 提示或删除结果输出；提示没有写入 stderr，也没有用 `args.json` 抑制。

**临时规避**：消费方读取第一个 JSON 值后停止解析，或改用库调用 `build_cleanup_plan()`；不建议依赖文本裁剪，因为提示内容可能变化。

**修复建议**：JSON 模式下所有人类可读提示写入 stderr，stdout 只保留一个 JSON 文档；补充 `clean --json` 与 `clean --json --apply --yes` 的解析测试。

#### DEF-002 `coverage` 规则匹配过宽

| 项目 | 内容 |
| --- | --- |
| 等级 | 中 |
| 状态 | 已修复（`c4fa6d9`；回归：`CleanerTests` coverage 用例） |
| 发现方式 | 运行时复现 |
| 影响需求 | FR-013 清理规则、FR-016 安全保护 |
| 影响范围 | 含名为 `coverage` 的源码目录或手工维护目录的项目 |

**修复前现象**：`ARTIFACT_RULES["node"]` 曾包含裸名称 `coverage`，`build_cleanup_plan()` 会匹配任意层级下名为 `coverage` 的目录，而不判断它是否是测试覆盖率输出。复现中 `app/coverage/keep.py` 被列入清理计划；若执行 `--apply --yes`，该源码目录会被删除。

**证据**：

```bash
mkdir -p "$TMP/app/coverage"
printf 'source\n' > "$TMP/app/coverage/keep.py"
projjan clean "$TMP/app"
# 计划中包含 .../app/coverage
```

**修复前根因**：规则按目录/文件名直接匹配，`coverage` 同时是常见工具输出目录名和可能的源码包名；当时没有内容特征或路径层级校验。

**临时规避**：清理前人工审查计划；对含 `coverage` 源码目录的项目显式指定不含 `node` 的规则集（如 `--rules python-cache,build`），或先重命名/移动该目录。

**修复建议**：移除通用 `coverage` 规则，改为只匹配已知覆盖率工具的输出特征（如 `coverage/lcov.info`、`coverage.xml`、`.coverage` 文件组合），或要求目录位于项目根且包含覆盖率产物。

#### DEF-003 单项目归档异常中断整批备份且不生成 manifest

| 项目 | 内容 |
| --- | --- |
| 等级 | 中 |
| 状态 | 已修复（`c4fa6d9`；回归：`test_batch_run_isolates_project_failures`, `test_backup_project_failure_reports_and_continues`） |
| 发现方式 | 运行时复现 + 源码审查 |
| 影响需求 | FR-009 策略执行、FR-010 归档、FR-011 manifest、FR-017 错误处理 |
| 影响范围 | 批量备份、权限不足、文件被占用、磁盘错误等场景 |

**修复前现象**：批量备份中任一项目的归档阶段抛出 `OSError`（如 `PermissionError`）时，旧版 `run_backup()` 会向上传播异常，CLI 以未捕获 traceback 结束，退出码 1；后续项目不再处理。按当时按项目写清单的布局，已完成项目可能已有自己的 `manifest-<时间戳>.json`，失败项目可能留下部分 `tar.gz` 但没有对应 manifest。

**证据**：构造两个项目，其中第二个项目含权限为 `000` 的文件，执行：

```bash
projjan backup "$TMP/alpha" "$TMP/beta" --dest "$TMP/out"
```

当前布局下观察到：退出码 1；stderr 出现 `PermissionError` traceback；`out/alpha/alpha-*.tar.gz`、`out/alpha/manifest-*.json` 和 `out/beta/beta-*.tar.gz` 存在；`out/beta/` 没有 manifest。v0.1.0 的旧运行目录布局复现时则只留下 `backup-*/alpha.tar.gz` 和 `beta.tar.gz`，整批没有 manifest。该复现只用于验证异常路径，未删除或修改任何真实项目。

**根因**：`backup.run_backup()` 的项目循环没有 `try/except` 隔离；`backup_project()` 的 `tarfile.add()` 异常直接传播；manifest 按项目写入，失败项目在异常前无法落盘；CLI 也没有捕获异常并转换为结构化错误。

**临时规避**：分批备份、先检查读权限、避免备份正在写入的大文件；失败后逐个检查项目目录，已完成项目可依赖其 manifest，失败项目不能依赖 manifest。

**修复建议**：按项目捕获 `OSError`，记录失败状态和原因，继续处理其余项目；即使存在失败也写出 manifest；CLI 输出失败摘要并返回非零码；补充权限拒绝、归档中断和部分成功的故障注入测试。

#### DEF-004 `clean --list-rules` 仍要求 `ROOT` 参数

| 项目 | 内容 |
| --- | --- |
| 等级 | 低 |
| 状态 | 已修复（`c4fa6d9`；回归：`test_list_rules_does_not_require_root`） |
| 发现方式 | 运行时复现 + 源码审查 |
| 影响需求 | FR-014 规则列表、FR-017 帮助与可用性 |
| 影响范围 | 只想查看规则、不执行清理的用户 |

**现象**：`projjan clean --list-rules` 退出 2，argparse 报 `the following arguments are required: roots`；必须写成 `projjan clean . --list-rules` 才能列出规则。TC-34 正是传入了 `.`，因此没有发现该问题。

**证据**：

```bash
projjan clean --list-rules
# usage: projjan clean [-h] ... roots [roots ...]
# projjan clean: error: the following arguments are required: roots
# exit=2
```

**根因**：`clean` 子命令把 `roots` 定义为 `nargs="+"` 的位置参数，`--list-rules` 只是普通布尔开关，argparse 在进入 `_cmd_clean` 前就完成了必填校验。

**临时规避**：传入任意已存在目录，例如 `projjan clean . --list-rules`。

**修复建议**：把 `roots` 改为 `nargs="*"`，在 `_cmd_clean` 中仅当未使用 `--list-rules` 时校验至少一个根；补充无根 `--list-rules` 的 CLI 测试。
