## 2. 项目概况

### 2.1 项目背景

开发者长期维护多个代码目录后，常出现三类问题：

1. 不清楚某个目录是否仍是有效项目、体积多大、最后何时修改。
2. 需要清理旧目录时，难以判断哪些内容已推送到远程、哪些只能本地归档。
3. 构建产物和依赖缓存占用大量空间，直接删除又存在误删源码或 Git 元数据的风险。

`proj_janitor` 针对上述问题提供一个本地命令行工具，以只读扫描、保守备份和白名单清理为基本原则，不依赖服务端或数据库。

### 2.2 项目目标

项目目标如下：

- 发现指定根目录下的项目，并识别常见项目标记。
- 统计项目体积、最后修改时间和 Git 工作区状态。
- 对已完整推送到 GitHub 的项目，仅记录远程 URL 与提交 SHA。
- 对不可从 GitHub 恢复的项目，生成 `tar.gz` 归档并记录 SHA-256。
- 生成结构化备份清单，并按清单恢复 Git 项目或归档项目；默认恢复到备份时的原始位置，也可用 `--dest` 恢复到新目录。
- 按白名单规则识别构建产物，默认只展示清理计划。
- 在显式确认后删除计划内条目，并保护项目根目录、`.git` 和符号链接。
- 提供文本与 JSON 输出及稳定退出码，便于脚本调用。

### 2.3 项目边界

本项目为本地单用户 CLI，不包含：

- 服务端、网络监听、外部 HTTP API。
- 数据库、数据迁移、多用户权限体系。
- 图形界面、移动端、浏览器插件。
- 云备份、远程推送、增量备份、自动保留策略。
- 独立的 `verify` 子命令、恢复覆盖/断点续传和 Git 远程提交预检。
- 定时任务、监控告警和集中运维平台。

## 7. 技术方案与关键决策

### 7.1 仅使用 Python 标准库

运行时不引入第三方依赖，降低安装、审计和供应链风险。测试使用标准库 `unittest`，构建仅依赖 `setuptools`。

### 7.2 保守备份策略

备份策略优先级为：

1. 指定 `--include-artifacts`：强制归档。
2. 指定 `--always-archive`：强制归档。
3. 通过全部 Git 可恢复性检查：记录远程 URL、分支、提交和上游，不生成归档。
4. 其他情况：生成 `tar.gz` 归档，并记录回退原因。

该顺序确保“显式要求归档”优先于“可恢复判断”，避免因判定逻辑变化导致用户预期落空。

### 7.3 URL-only 的安全门槛

URL-only 记录依赖远程仓库长期可用，因此只在本地能够证明“提交已完整推送到受支持的 GitHub 远程”时启用。检查包括：

- `.git` 存在，HEAD 可解析且不是 detached 状态。
- 工作区干净、无 stash。
- 当前分支存在远程与上游。
- 远程 URL 为受支持的 GitHub 形式；允许 HTTPS URL 内嵌 PAT，但清单和输出只保存脱敏 URL。
- HEAD 已包含于上游，且不领先上游。
- 所有本地分支均已完整推送。
- 所有本地 tag 均已推送，且与远程同名 tag 指向同一对象；没有本地 tag 时不做额外远程查询。
- 无子模块或 Git LFS。
- 被忽略文件仅为已知构建产物。

任一检查失败均回退归档，并在清单中记录原因。标签校验需要访问远程（`git ls-remote --tags --refs`）；远程不可达时保守回退为归档。

### 7.4 manifest v2

每次备份按项目生成 `DEST/<项目名>/manifest-<时间戳>.json`，包含工具名、版本、参数、创建时间和该项目记录；批量运行会为每个项目各写一份清单。记录区分 `git` 与 `archive` 两种策略，归档记录包含 SHA-256，便于交付校验。`restore` 读取同一 schema v2 清单，按记录恢复项目。

### 7.5 白名单清理与默认干跑

清理仅匹配预定义规则中的构建产物和依赖缓存。默认不删除，只有同时满足 `--apply` 和确认条件才执行。非交互环境必须显式传入 `--yes`，否则退出码为 2。

### 7.6 单层项目发现

默认只检查根目录本身及其直接子目录，不递归遍历整个文件树。该决策避免在大型目录上产生不可控耗时，也降低把嵌套目录误判为独立项目的风险。

### 7.7 明确的退出码

- `0`：成功。
- `1`：根目录、项目处理或删除过程存在失败。
- `2`：参数错误、非交互删除未确认或用户取消。

### 9.2 其他缺陷与风险

- `clean --json` 曾混入人类可读文本，已在 `2884075` 修复，stdout 现在是纯 JSON。
- `coverage` 规则曾匹配普通源码目录，已在 `2884075` 收紧到项目根和覆盖率产物标记，并增加回归测试。
- Git 命令失败或超时时状态显示为 `unknown`，缺少针对性故障注入测试。
- 清理计划去重依赖 `_collect_projects` 的项目路径去重；早期关于“重叠根目录重复计数”的描述未能复现，源代码显示重复项目会被过滤，应作为历史问题记录。
- 备份清单中的远程 URL 可能包含组织或仓库信息；新版本会去除 HTTPS 用户信息，但归档内的 `.git/config` 仍可能保留原始 PAT。
- `restore` 批量执行中途失败时不会回滚已完成项目；Git 恢复也没有远程提交预检。
- 若文档示例引用外部项目，必须使用占位符，不得写入真实凭据。

### 9.3 经验教训

1. 对涉及删除的工具，默认干跑和显式确认是最有效的安全措施。
2. “可恢复”不能只看远程是否存在，还必须验证工作区、上游包含关系和未推送分支。
3. 批处理应隔离单项目失败，避免一个权限错误导致整批任务中止。
4. JSON 模式应保持纯结构化输出，进度和提示应写入标准错误。
5. 文档中的体积、测试数量和提交号应以可复核命令为准，避免凭记忆填写。
