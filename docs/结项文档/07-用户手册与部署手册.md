## 3. 工具概述与安全边界

### 3.1 工具能做什么

| 能力 | 命令 | 说明 |
| --- | --- | --- |
| 盘点项目 | `scan` | 发现带项目标记的目录，统计体积、最后修改时间、Git 分支和工作区状态 |
| 轻量备份 | `backup` | 对可恢复项目只记录 GitHub URL、分支、上游和提交 SHA |
| 归档备份 | `backup` | 对不可恢复项目生成 `tar.gz`，记录大小、SHA-256 和回退原因 |
| 查看清理计划 | `clean` | 按白名单规则列出构建产物和依赖缓存，默认不删除 |
| 执行清理 | `clean --apply` | 在显式确认后删除计划内条目 |
| 脚本集成 | `scan --json`、`clean --json` | 输出结构化结果；`clean --json` 存在已知输出污染，见 3.5 节 |

### 3.2 工具不做什么

- 不提供 `restore` 子命令；恢复需要按 manifest 手工执行。
- 不推送代码、不创建远程仓库、不做云备份或异地复制。
- 不加密备份、不管理密钥、不做访问控制和审计日志签名。
- 不做增量备份、去重、自动保留策略或配额管理。
- 不提供数据库、Web 服务、图形界面、HTTP API 或定时任务。
- 不保证 Windows、macOS、网络文件系统或非 UTF-8 环境可用。
- 不替代 Git 本身的备份策略，也不验证远程仓库是否仍存在某个提交。

### 3.3 三条安全原则

1. **先扫描，再备份，最后清理。** 不要跳过盘点直接删除。
2. **清理默认 dry-run。** 必须人工审查计划，再决定是否 `--apply`。
3. **备份目录必须在被清理项目之外。** 不要把 `--dest` 放在任何 `ROOT` 内部，避免归档自身、递归增长或清理误伤。

工具自身还会执行以下保护：

- 永不删除项目根目录；
- 永不进入或删除 `.git`；
- 不跟随符号链接目录或文件；
- 删除前重新解析路径，拒绝逃逸项目根的目标；
- 非交互环境执行 `clean --apply` 必须显式提供 `--yes`。

### 3.5 已知缺陷提醒（使用前必读）

以下问题在 v0.1.0 中确认存在且未修复，详细证据见 06 第 8 章：

| 编号 | 问题 | 对使用者的影响 | 建议 |
| --- | --- | --- | --- |
| DEF-001 | `clean --json` 在 JSON 后追加提示文本 | 严格 JSON 解析失败 | 不要直接消费 `clean --json`；改用库调用或等待修复 |
| DEF-002 | `coverage` 规则匹配任意同名目录 | 名为 `coverage` 的源码目录可能被误删 | 清理前逐项审查；必要时显式选择规则 |
| DEF-003 | 单项目归档异常中断整批备份 | 可能留下部分归档且没有 manifest | 分批备份、先检查权限；失败后手工核对目录 |
| DEF-004 | `clean --list-rules` 仍要求 `ROOT` | 不能直接单独列出规则 | 使用 `projjan clean . --list-rules` |

不要因为“测试 38 项全部通过”就认为上述缺陷不存在；测试通过率和缺陷状态是两件事。

## 4. 部署方案

### 4.1 部署形态

`proj_janitor` 是本地单用户命令行工具，部署形态如下：

| 维度 | 结论 |
| --- | --- |
| 运行位置 | 用户工作站或本地开发机 |
| 进程模型 | 一次性前台进程，执行完即退出 |
| 服务端 | 无 |
| 数据库 | 无 |
| 网络监听 | 无 |
| 后台守护进程 | 无 |
| 定时任务 | 工具不提供，需用户自行用 `cron`/`systemd timer` 包装（未验证） |
| 多用户 | 不提供权限体系；按操作系统用户隔离 |
| 配置 | 无配置文件；行为由命令行参数和代码内规则决定 |

因此，“部署”实质上是：准备 Python 环境、安装包、准备 Git、规划备份目录、验证命令可用。

### 4.2 环境要求

| 项目 | 要求 | 说明 |
| --- | --- | --- |
| 操作系统 | Linux（已验证） | Windows/macOS 未验证，不声明官方支持 |
| 架构 | x86_64（已验证） | 其他架构理论可用，未验证 |
| Python | 3.10 及以上 | `pyproject.toml` 声明 `>=3.10`；实测 3.12.3 |
| pip | 可用 | 安装 wheel 或源码需要 |
| Git | 建议 2.x | `backup` 的 URL-only 判定和 Git 状态读取需要；无 Git 时相关能力降级 |
| Shell | Bash/POSIX Shell | 示例使用 Bash |
| 磁盘 | 取决于备份规模 | 归档大小约为项目体积减去被排除制品；`.git` 会增加体积 |
| 权限 | 普通用户 | 不需要 root；不要用 root 执行日常清理 |
| 网络 | 不需要 | 工具不访问网络；URL 只作为字符串记录 |

### 4.3 部署拓扑

```text
┌──────────────────────────────┐
│ 用户终端（Bash）              │
│ projjan scan/backup/clean    │
└──────────────┬───────────────┘
               │ 参数、stdout/stderr、退出码
               ▼
┌──────────────────────────────┐
│ proj_janitor CLI（Python）    │
│ scanner / backup / cleaner   │
└───────┬───────────────┬──────┘
        │               │
        ▼               ▼
┌──────────────┐  ┌────────────────────┐
│ 本地文件系统  │  │ git 子进程（本地）  │
│ 项目、归档    │  │ status/rev-parse 等 │
└──────────────┘  └────────────────────┘
        │
        ▼
┌──────────────────────────────┐
│ 备份目录（独立磁盘/目录）      │
│ backup-*/ *.tar.gz manifest  │
└──────────────────────────────┘
```

没有服务端、数据库、消息队列、容器编排或外部 API。备份目录是唯一需要长期保留的运行产物。

### 4.4 安装方式选择

| 方式 | 适用场景 | 优点 | 限制 |
| --- | --- | --- | --- |
| 源码直接运行 | 临时试用、开发调试 | 不安装，`python3 -m proj_janitor` 即可 | 每次需在源码目录或设置 `PYTHONPATH` |
| 虚拟环境 + `pip install -e .` | 推荐日常使用 | 隔离依赖、入口命令可用、改代码立即生效 | 需要 `venv`/`ensurepip` 可用 |
| 虚拟环境 + wheel | 交付、固定版本 | 安装包独立、便于归档 | 需要先构建 wheel；本次未提供预构建 wheel |
| `pip install --user .` | 无法创建 venv 时的备选 | 不需要 root | 本结项未对该方式做安装验证；受用户 site-packages 影响 |

推荐：每个使用者一个独立虚拟环境，备份目录放在独立磁盘或独立目录，不使用 root。

### 4.5 目录与权限规划

建议布局：

```text
$HOME/
├── .venvs/
│   └── projjan/                 # 虚拟环境
├── src/
│   └── proj_janitor/            # 源码副本
├── backups/
│   └── projects/                # 备份根目录，独立于项目目录
└── projects/                    # 被扫描/清理的项目
```

规划要点：

- 备份根目录 `--dest` 不要位于任何被扫描或被清理的项目内部。
- 备份目录与源码目录尽量放在不同磁盘或不同挂载点，降低同时损坏风险。
- 备份目录权限建议 `0700` 或按组织要求收紧；归档可能包含源码、配置和 `.git` 历史。
- 不要用 root 运行 `clean`；普通用户权限足以处理自己的项目，也能降低误删系统目录的风险。
- 如果项目位于 NFS/SMB 等网络文件系统，先在小样本上验证；当前未验证这些文件系统。

### 4.6 升级与回滚

v0.1.0 没有自动升级机制，也没有数据库迁移。建议：

1. 保留当前可用的虚拟环境和 wheel/源码副本。
2. 在独立目录安装新版本，先执行 `projjan --version` 和 `scan` 冒烟。
3. 确认新版本能读取旧 manifest（当前只有 schema v2，无迁移工具）。
4. 再切换日常使用的 `PATH` 或虚拟环境。
5. 如新版本异常，切回旧虚拟环境；不要删除旧备份。

注意：manifest 的 `schema_version` 用于标识格式代际，但当前没有迁移工具。未来版本不应被假定无条件兼容旧 manifest；升级前应保留原始 manifest 和归档。

### 4.7 卸载

```bash
# 在虚拟环境中卸载
pip uninstall proj-janitor

# 删除虚拟环境（确认不再需要后）
rm -rf "$HOME/.venvs/projjan"
```

卸载不会删除备份目录、manifest 或归档；这些需要按保留策略单独处理。不要为了“卸载干净”而删除备份。

# 预期：显示 scan/backup/clean 子命令

# 预期：输出 JSON 数组；退出码 0

### 5.8 安装失败排查

| 现象 | 可能原因 | 处理 |
| --- | --- | --- |
| `projjan: command not found` | 虚拟环境未激活，或脚本目录不在 `PATH` | 激活 venv；检查 `$VIRTUAL_ENV/bin` 或 `$HOME/.local/bin` |
| `No module named proj_janitor` | 未安装，或使用了错误的 Python | `python3 -m pip show proj-janitor`；确认 `which python3` |
| `python3 -m venv` 报 ensurepip 缺失 | 系统未安装 `python3-venv` | 安装系统包，或改用 `pip install --user .` |
| 构建 wheel 失败 | `setuptools` 版本过低或缺少 `build` | 升级构建工具；确认 `pyproject.toml` 的 `setuptools>=68` |
| `projjan scan` 显示 Git 状态为 `-`/`unknown` | Git 未安装、仓库损坏、权限不足或命令超时 | 手动执行 `git -C <path> status` 排查 |
| `pip install` 访问网络失败 | 环境禁止联网，且 pip 尝试解析构建依赖 | 使用已构建 wheel + `--no-index`；或配置内部镜像（需组织批准） |

## 6. 用户操作手册

### 6.1 快速开始

```bash
# 1. 盘点
projjan scan ~/projects

# 2. 备份 dry-run，确认策略和目标目录
projjan backup ~/projects --dest ~/backups/projects --dry-run

# 3. 实际备份
projjan backup ~/projects --dest ~/backups/projects

# 4. 查看清理计划（不删除）
projjan clean ~/projects

# 5. 人工审查后执行清理
projjan clean ~/projects --apply
```

第 5 步在交互终端会要求输入 `y`/`yes`；在脚本或非 TTY 环境中必须加 `--yes`，否则会拒绝删除并退出 2。

### 6.2 `scan`：盘点项目

语法：

```bash
projjan scan ROOT [ROOT ...] [--all] [--json]
```

常用示例：

```bash
# 默认只发现带项目标记的直接子目录
projjan scan ~/projects

# 把没有标记的直接子目录也列出来
projjan scan ~/projects --all

# 多个根
projjan scan ~/projects ~/archive

# JSON，供脚本消费
projjan scan ~/projects --json
```

发现规则：

- 扫描根自身是项目时，只返回该根，不再扫描其子目录。
- 扫描根自身不是项目时，只检查直接子目录，不递归更深层。
- 默认跳过名称以 `.` 开头的目录、符号链接目录和无项目标记的目录。
- `--all` 只放宽“无标记”这一条，点号目录和符号链接目录仍跳过。
- 多个根产生同一路径时只保留首次出现的项目。

输出列：

| 列 | 含义 |
| --- | --- |
| `PROJECT` | 项目目录名 |
| `SIZE` | 文件字节数之和，人类可读格式 |
| `BRANCH` | Git 分支；无 Git 或读取失败为 `-` |
| `STATE` | `clean`、`dirty`、`unknown` 或 `-` |
| `MARKERS` | 识别到的项目标记 |
| `MODIFIED` | 本地时间 `YYYY-MM-DD HH:MM`；无文件为 `-` |

退出码：

- `0`：根路径均有效（即使没有发现项目）；
- `1`：至少一个根路径不存在、不可读或不是目录；其他根继续处理；
- `2`：参数错误。

注意：体积是文件字节数之和，不是磁盘占用；不统计目录元数据，不跟随符号链接。

### 6.3 `backup`：备份项目

语法：

```bash
projjan backup ROOT [ROOT ...] --dest DEST [--dry-run]
                 [--include-artifacts] [--always-archive]
```

常用示例：

```bash
# 先看计划，不写盘
projjan backup ~/projects --dest ~/backups/projects --dry-run

# 实际备份
projjan backup ~/projects --dest ~/backups/projects

# 连构建产物和依赖缓存一起归档
projjan backup ~/projects --dest ~/backups/projects --include-artifacts

# 所有项目都归档，即使可以从 GitHub 恢复
projjan backup ~/projects --dest ~/backups/projects --always-archive
```

策略选择顺序：

1. `--include-artifacts`：强制归档，原因 `include_artifacts`；
2. `--always-archive`：强制归档，原因 `always_archive`；
3. Git 可恢复性检查通过：只记录 Git 信息，不生成归档；
4. 其他情况：归档，原因取可恢复性失败原因或 `not recoverable from GitHub`。

URL-only 的条件很严格，至少包括：

- 工作区干净；
- 没有 stash、submodule、LFS 等未覆盖状态；
- 所有本地分支都已推送；
- 当前 HEAD 包含在上游；
- 远程是无内嵌凭据的 GitHub URL。

只要有一条不满足，就会回退为归档。URL 中含用户名/令牌的远程一律拒绝 URL-only，避免把凭据写进 manifest。

`--dest` 规则：

- 不存在时，实际运行会创建；
- 已存在但不是目录时，报错并退出 1；
- 建议使用绝对路径或 `~` 展开路径；
- 不要放在被备份项目内部。

输出示例：

```text
Dry run. Backup directory would be: /home/user/backups/backup-20261022-153000
  [git] demo: https://github.com/owner/demo.git @ 012d539e5803
  [archive] old-tool: 12.4 MiB -> /home/user/backups/backup-20261022-153000/old-tool.tar.gz (working tree is not clean)
```

实际运行后，运行目录包含：

```text
backup-20261022-153000/
├── old-tool.tar.gz
└── manifest.json
```

`demo` 不生成归档，只在 `manifest.json` 中保留一条 `strategy: "git"` 记录。

退出码：

- `0`：全部项目成功，manifest 已写入；
- `1`：没有发现项目、`DEST` 不是目录、或部分根路径失败；
- `2`：参数错误；
- 归档阶段未捕获异常：可能以 Python traceback 结束，退出码 1，且 manifest 可能缺失（DEF-003）。

重要限制：

- 没有发现项目时，命令输出 `No projects found.` 并退出 1，且不会检查 `DEST` 是否合法。
- 归档包含 `.git`，体积可能明显大于工作区可见文件。
- 工具不联网确认远程是否仍有该提交；URL-only 记录的 `verified` 是 `local-ref`，不是远程验证。
- 批量备份没有失败隔离；一个项目归档失败可能中断整批并跳过 manifest。

### 6.4 `clean`：查看和执行清理

语法：

```bash
projjan clean ROOT [ROOT ...] [--rules RULES] [--apply] [--yes]
                 [--json] [--list-rules]
```

常用示例：

```bash
# 默认 dry-run，只显示计划
projjan clean ~/projects

# 只看某几类规则
projjan clean ~/projects --rules node,python-cache

# 执行删除（交互确认）
projjan clean ~/projects --apply

# 非交互环境执行删除
projjan clean ~/projects --apply --yes

# 列出规则（必须带一个占位根，见 DEF-004）
projjan clean . --list-rules
```

规则表：

| 规则 | 匹配名称 |
| --- | --- |
| `python-cache` | `__pycache__`、`.pytest_cache`、`.mypy_cache`、`.ruff_cache`、`*.pyc`、`.coverage`、`htmlcov` |
| `python-env` | `.venv`、`venv`、`.tox`、`.nox`、`*.egg-info` |
| `node` | `node_modules`、`.next`、`.nuxt`、`.svelte-kit`、`.turbo`、`.parcel-cache`、`coverage` |
| `build` | `build`、`dist`、`out`、`target`、`CMakeFiles`、`.gradle` |
| `editor` | `.cache`、`.DS_Store`、`Thumbs.db` |

`--rules` 是“只选这些规则”的白名单，不是“排除这些规则”的黑名单。例如只要清理 Python 缓存和构建产物，应写：

```bash
projjan clean ~/projects --rules python-cache,build
```

这不会包含 `node`、`python-env` 和 `editor`。

删除保护：

- 不删除项目根；
- 不进入或删除 `.git`；
- 不跟随符号链接；
- 目标必须位于项目根内；
- 删除前重新解析路径并校验；
- 非交互环境缺少 `--yes` 时拒绝删除，退出 2。

`safe` 操作流程：

1. 先运行不带 `--apply` 的命令；
2. 逐项检查 `PATH` 是否确实为构建产物；
3. 对 `coverage`、`build`、`dist`、`target` 等通用名称特别警惕；
4. 确认当前项目已有可用备份或版本控制；
5. 再执行 `--apply`；
6. 删除后检查源码、`.git` 和关键配置仍在。

`clean --json` 的已知问题：

- dry-run 时会在 JSON 后追加 `Dry run...`；
- `--apply --yes` 时会在 JSON 后追加 `Removed ...`；
- 严格 JSON 解析器会报 `Extra data`。

如果必须脚本化，优先调用 `proj_janitor.cleaner.build_cleanup_plan()`，或等待 DEF-001 修复；不要把 `clean --json` 的输出直接交给 `jq` 等严格解析器。

### 6.5 恢复

当前没有 `restore` 子命令。按 manifest 手工恢复。

#### 6.5.1 Git 策略

manifest 记录示例字段：

```json
{
  "strategy": "git",
  "remote_url": "https://github.com/owner/demo.git",
  "branch": "main",
  "commit": "012d539e58035346fc01fda81b8bc06c1440d4f3",
  "upstream": "origin/main"
}
```

恢复：

```bash
git clone https://github.com/owner/demo.git demo-restored
cd demo-restored
git checkout 012d539e58035346fc01fda81b8bc06c1440d4f3
```

注意：

- 远程必须仍存在且仍包含该提交；工具没有做远程验证。
- 如果远程已删除、改为私有或提交被强制推送掉，URL-only 记录不足以恢复，只能依赖其他备份。
- `commit` 是完整 SHA；不要只使用前 12 位做长期恢复记录。

#### 6.5.2 archive 策略

```bash
# 先校验归档完整性
sha256sum old-tool.tar.gz
# 与 manifest 中的 sha256 比较

# 解压到目标父目录；归档顶层目录为项目名
tar -xzf old-tool.tar.gz -C /path/to/restore-parent

# 检查结果
ls -la /path/to/restore-parent/old-tool
```

注意：

- 归档包含 `.git`，解压后仍是 Git 仓库；但不要假定它等同于完整的远程历史备份。
- 归档可能包含敏感配置和凭据；解压和分享前确认权限与脱敏要求。
- 归档只保证文件内容，不保证权限位、扩展属性、硬链接、ACL 等全部元数据。

### 6.6 典型工作流

#### 场景 A：盘点旧项目，决定去留

```bash
projjan scan ~/projects
projjan scan ~/projects --json > projects.json
```

先看体积、最后修改时间、Git 状态，再决定备份或清理；不要仅凭体积删除。

#### 场景 B：备份后清理构建产物

```bash
projjan backup ~/projects --dest ~/backups/projects --dry-run
projjan backup ~/projects --dest ~/backups/projects
projjan clean ~/projects
projjan clean ~/projects --apply
```

确认 manifest 已生成、归档哈希已记录，再执行清理。

#### 场景 C：只清理缓存，不动依赖

```bash
projjan clean ~/projects --rules python-cache,editor
```

这不会删除 `node_modules` 或虚拟环境。

#### 场景 D：迁移前完整归档

```bash
projjan backup ~/projects --dest /mnt/backup/projects --include-artifacts
```

完整归档体积大，但保留构建产物和依赖；确认目标磁盘空间足够。

#### 场景 E：多根目录分批处理

```bash
projjan scan ~/work ~/personal ~/archive
projjan backup ~/work --dest ~/backups/work
projjan backup ~/personal --dest ~/backups/personal
```

分批可以降低 DEF-003 的影响：一个批次失败不会拖垮其他批次。

### 6.7 安全操作检查表

执行 `clean --apply` 前：

- [ ] 已运行 `scan`，确认项目范围正确。
- [ ] 已运行 `backup`，manifest 存在且记录完整。
- [ ] 已运行不带 `--apply` 的 `clean`，并逐项审查路径。
- [ ] 特别检查 `coverage`、`build`、`dist`、`target` 等通用名称。
- [ ] 确认 `--dest` 不在任何被清理项目内部。
- [ ] 确认当前用户不是 root。
- [ ] 确认没有其他进程正在写入这些目录。
- [ ] 确认磁盘和备份可读，知道如何恢复。

执行后：

- [ ] 检查源码、`.git` 和关键配置仍在。
- [ ] 检查删除摘要与计划数量一致。
- [ ] 检查 stderr 是否有逐项错误。
- [ ] 记录本次操作、时间、范围和结果。

### 6.8 输出与退出码

| 退出码 | 含义 | 常见命令 |
| --- | --- | --- |
| `0` | 成功（扫描无项目也可能是 0） | `scan`、`backup`、`clean` |
| `1` | 根路径失败、没有项目、部分备份/清理失败、目标不是目录 | `scan`、`backup`、`clean` |
| `2` | 参数错误、非交互拒绝删除、用户取消 | 所有命令 |

脚本中应同时检查退出码和 stderr，不要只看 stdout。`backup` 的未捕获归档异常可能以 traceback 结束，退出码为 1，但不属于结构化错误。

## 7. 运维手册

### 7.1 运维边界

本工具没有服务进程、端口、数据库连接池、队列或定时任务，因此不需要传统的服务监控、健康检查、日志轮转和容量告警。运维工作主要是：

- 保证 Python/Git 环境可用；
- 保证备份目录可写、空间充足、权限正确；
- 定期检查 manifest 和归档完整性；
- 管理备份保留、异地副本和敏感信息；
- 处理失败批次和误删事件。

工具使用者通常就是运维责任人；如果是团队使用，应明确谁负责备份介质和恢复演练。

### 7.2 日常检查

建议按周或按月执行：

```bash
# 版本与入口
projjan --version

# 备份目录空间
df -h /path/to/backups

# 最近一次备份的运行目录
ls -lt /path/to/backups | head

# manifest 是否可解析
python3 -m json.tool /path/to/backups/backup-*/manifest.json > /dev/null && echo OK

# 抽查归档哈希（以 manifest 中的值为准）
sha256sum /path/to/backups/backup-*/old-tool.tar.gz
```

检查要点：

- 每次实际备份都应有 `manifest.json`；没有 manifest 的运行目录视为不完整。
- manifest 中的 `sha256` 应与归档实际哈希一致。
- 归档数量、项目数量与预期一致；缺失项目要查明原因。
- 备份目录不要被误放进被清理项目；如果发生，先停止清理并检查。
- 磁盘剩余空间应能容纳下一轮完整备份；工具没有配额和保留策略。

### 7.3 备份保留与介质

工具不提供自动保留策略，以下为建议，不是工具功能：

- 至少保留两份独立副本，其中一份在不同磁盘或不同机器。
- 重要项目在清理源目录前，确认归档可解压、哈希匹配。
- 不要把唯一备份放在正在使用的项目磁盘上。
- 定期做恢复演练；只验证“归档存在”不等于“可以恢复”。
- 备份可能含密钥、令牌、`.env`、数据库转储和个人信息；按组织要求加密、限权或脱敏。
- 删除旧备份前确认保留期和合规要求；工具不会自动清理旧备份。

### 7.4 日志与审计

工具没有内置日志文件，也没有审计日志签名。可用方式：

```bash
projjan backup ~/projects --dest ~/backups/projects \
  > /path/to/logs/backup-$(date +%Y%m%d-%H%M%S).out \
  2> /path/to/logs/backup-$(date +%Y%m%d-%H%M%S).err
```

建议保留：

- 命令、参数、执行时间、执行用户；
- stdout/stderr；
- 退出码；
- manifest 和归档；
- 清理计划的人工确认记录（如终端截图或工单）。

注意：stdout 可能包含项目名、路径、Git URL；不要公开粘贴含敏感信息的日志。

### 7.5 故障处理

| 现象 | 可能原因 | 处理 |
| --- | --- | --- |
| `command not found` | venv 未激活、PATH 不含脚本目录 | 激活 venv；检查 `which projjan` |
| `ModuleNotFoundError` | 包未安装或 Python 版本不对 | `python3 -m pip show proj-janitor`；确认 Python 3.10+ |
| `scan` 的 Git 状态为 `unknown` | Git 命令失败、超时、仓库损坏或权限不足 | 手动执行 `git -C <path> status`；检查 `safe.directory` 和权限 |
| `backup` 输出 `No projects found.` 并退出 1 | 根目录没有项目标记，或根路径错误 | 先用 `scan` 确认；必要时用 `--all` 查看普通目录 |
| `destination is not a directory` | `--dest` 指向了文件 | 改为目录路径，或先创建目录 |
| 备份中途 traceback、退出 1 | 归档权限、磁盘满、文件被占用（DEF-003） | 检查运行目录；部分归档不可信；修复权限/空间后重跑，并手工确认 manifest |
| `clean` 拒绝删除、退出 2 | 非交互环境缺少 `--yes` | 加 `--yes`，或改在交互终端执行 |
| `clean` 报 `unknown rule(s)` | `--rules` 拼写错误 | `projjan clean . --list-rules` 查看可用规则 |
| `clean --json` 解析失败 | JSON 后追加了提示（DEF-001） | 改用库调用，或只取第一个 JSON 值；不要直接 `jq` |
| 误删了 `coverage` 源码目录 | `coverage` 规则过宽（DEF-002） | 立即停止后续清理；从备份/版本控制恢复；记录事件 |
| manifest 缺失 | 归档阶段异常，或运行被中断 | 检查同目录归档；不要假定备份完整；重跑并确认 manifest |
| 归档哈希不匹配 | 文件损坏、复制不完整、磁盘错误 | 从其他副本恢复；不要使用该归档覆盖源目录 |

### 7.6 升级与回滚操作

```bash
# 记录当前版本
projjan --version

# 在独立 venv 安装新版本并验证
python3 -m venv /path/to/venv-new
source /path/to/venv-new/bin/activate
python3 -m pip install /path/to/new/dist/*.whl
projjan --version
projjan scan /path/to/sample --json

# 确认后切换 PATH；旧 venv 保留一个版本周期
```

回滚：

```bash
source /path/to/venv-old/bin/activate
projjan --version
```

不要删除旧 manifest 或归档；新版本可能无法读取旧格式，反之亦然。

### 7.7 安全事件处理

#### 7.7.1 manifest 中出现凭据

URL-only 会拒绝含内嵌凭据的远程 URL，但归档本身可能包含 `.env`、密钥或历史提交中的凭据。发现凭据后：

1. 立即限制 manifest/归档所在目录权限；
2. 轮换已暴露的令牌、密码或密钥；
3. 评估是否需要删除或重新生成备份；
4. 不要在工单、聊天或文档中粘贴凭据；
5. 记录事件范围和处理结果。

#### 7.7.2 误删项目内容

`clean --apply` 没有回收站或撤销命令。处理顺序：

1. 立即停止后续清理和其他写入；
2. 检查是否有 Git 提交、IDE 本地历史、文件系统快照或备份；
3. 从归档或 Git 恢复；
4. 如果使用 `coverage`/`build` 等通用规则，检查是否还有其他误删；
5. 记录根因，调整规则或操作流程。

#### 7.7.3 备份不可用

- 先校验归档哈希和 manifest；
- 尝试其他副本或异地副本；
- 不要用损坏的归档覆盖唯一源目录；
- 如果远程 URL-only 记录是唯一副本，确认远程仓库和提交是否仍存在。

## 9. 常见问题（FAQ）

### Q1：`scan` 为什么没有发现我的项目？

默认只检查扫描根的直接子目录，并要求存在项目标记（`.git`、`pyproject.toml`、`package.json` 等）。先确认目录层级和标记；需要查看无标记目录时加 `--all`。

### Q2：为什么有的项目没有生成 `.tar.gz`？

它满足 URL-only 条件，manifest 中 `strategy` 为 `git`，只记录远程 URL 和提交 SHA。使用 `--always-archive` 可强制归档。

### Q3：URL-only 记录能保证恢复吗？

不能。工具只验证本地引用和 URL 形式，不联网确认远程是否仍存在该提交。远程删除、强制推送或仓库转私有都可能导致无法恢复；重要项目应保留归档或其他备份。

### Q4：`clean` 默认会删除吗？

不会。默认 dry-run，只显示计划。必须 `--apply`；非交互环境还必须 `--yes`。

### Q5：为什么 `clean --apply` 被拒绝？

标准输入不是 TTY 且没有 `--yes`。这是安全保护，不是故障。交互终端执行并输入 `y`，或显式加 `--yes`。

### Q6：`--rules` 是排除列表吗？

不是。它是白名单，只启用列出的规则。未知规则会报错；空值会被忽略，全部为空时报错。

### Q7：为什么 `clean --json` 不能被 `jq` 解析？

DEF-001：JSON 后追加了 dry-run 或删除摘要。当前应改用库调用，或只解析第一个 JSON 值；不要依赖文本裁剪。

### Q8：可以删除 `.git` 或项目根吗？

不能。工具明确跳过 `.git`，并拒绝删除项目根或逃逸项目根的路径。即使规则误匹配，也不应绕过这些保护。

### Q9：备份目录应该放在哪里？

放在被扫描/清理项目之外，最好是独立磁盘或独立挂载点。不要把 `--dest` 放在任何 `ROOT` 内部。

### Q10：如何校验归档？

用 `sha256sum <archive>` 与 manifest 中的 `sha256` 比较。当前没有内置校验命令；这是已知限制 L-05。

### Q11：支持 Windows 吗？

未验证，不声明官方支持。路径分隔符、权限、符号链接和 Git 行为可能不同；如需要，应先做兼容性测试。

### Q12：如何完全卸载？

在 venv 中 `pip uninstall proj-janitor`，删除 venv；备份目录和 manifest 需按保留策略单独处理，工具不会自动删除。

### 10.1 命令速查

```bash
# 版本/帮助
projjan --version
projjan --help
projjan scan --help
projjan backup --help
projjan clean --help

# 扫描
projjan scan ROOT
projjan scan ROOT --all

# 备份
projjan backup ROOT --dest DEST --dry-run
projjan backup ROOT --dest DEST
projjan backup ROOT --dest DEST --include-artifacts
projjan backup ROOT --dest DEST --always-archive

# 清理
projjan clean ROOT

projjan clean ROOT --apply
projjan clean ROOT --apply --yes
projjan clean . --list-rules

# 测试
python3 -m unittest discover -s tests -v
```

### 10.2 规则与保护速查

| 规则 | 典型目标 | 风险提示 |
| --- | --- | --- |
| `python-cache` | `__pycache__`、`.pytest_cache`、`*.pyc` | 一般安全；确认没有手工维护的同名目录 |
| `python-env` | `.venv`、`venv`、`.tox` | 删除后需重建环境；确认没有未提交的本地包 |
| `node` | `node_modules`、`.next`、`coverage` | `coverage` 可能误匹配源码目录（DEF-002） |
| `build` | `build`、`dist`、`out`、`target` | 可能包含待发布产物；确认可重建 |
| `editor` | `.cache`、`.DS_Store`、`Thumbs.db` | 一般安全；`.cache` 可能含本地状态 |

### 10.3 退出码速查

| 退出码 | 含义 |
| --- | --- |
| `0` | 成功；`scan` 无项目也可能为 0 |
| `1` | 根路径失败、无项目、部分失败、目标不是目录、清理逐项错误 |
| `2` | 参数错误、非交互拒绝删除、用户取消 |

### 10.4 manifest 字段速查

| 字段 | 说明 |
| --- | --- |
| `schema_version` | 固定为 `2` |
| `created_at` | UTC ISO 8601 时间 |
| `tool` | `proj-janitor` |
| `version` | `0.1.0` |
| `include_artifacts` | 是否包含构建产物/依赖缓存 |
| `always_archive` | 是否强制归档 |
| `records` | 每个项目一条记录 |
| `records[].strategy` | `git` 或 `archive` |
| `records[].archive` | 归档绝对路径；Git 策略为 `null` |
| `records[].sha256` | 归档 SHA-256；Git 策略为 `null` |
| `records[].remote_url` | Git 策略的远程 URL |
| `records[].commit` | Git 策略的完整提交 SHA |
| `records[].fallback_reason` | 归档策略的回退原因 |

完整字段和示例见 `05-接口与CLI文档.md` 第 10 章。

### 10.5 术语

| 术语 | 说明 |
| --- | --- |
| 项目标记 | 用于判断目录是否为项目的固定文件/目录名，如 `.git`、`pyproject.toml` |
| URL-only | 只记录 GitHub 远程 URL 与提交 SHA，不生成归档 |
| 归档策略 | 生成 `tar.gz` 并记录 SHA-256 |
| dry-run | 只展示计划，不写盘、不删除 |
| manifest | 备份运行清单 `manifest.json`，schema v2 |
| 可恢复性 | 本地 Git 状态是否满足从 GitHub 恢复的条件 |
| 制品 | 构建产物、依赖缓存、编辑器缓存等可重建内容 |
